Encryption Fundamentals Cifrado: Conceptos Base

Before diving into KMS, it's essential to understand the three encryption models used in the cloud. Each model differs in where the encryption and decryption happen and who holds the key. Knowing these distinctions is fundamental for choosing the right approach and for the exam. Antes de entrar en KMS, es fundamental entender los tres modelos de cifrado usados en la nube. Cada modelo difiere en dónde ocurre el cifrado/descifrado y quién tiene la clave. Conocer estas diferencias es clave para elegir el enfoque correcto y para el examen.

Encryption in Flight — How TLS Works Cifrado en Tránsito — Cómo Funciona TLS

The client encrypts data using a TLS certificate before sending it over the network. No intermediate server can read the packets. Only the target server can decrypt them. This protects against man-in-the-middle attacks. El cliente cifra los datos usando un certificado TLS antes de enviarlos por la red. Ningún servidor intermedio puede leer los paquetes. Solo el servidor destino puede descifrarlos. Esto protege contra ataques de man-in-the-middle.

Server-Side Encryption at Rest Cifrado del Lado del Servidor en Reposo

Data arrives at the server (possibly over HTTPS). The server uses a data key to encrypt the data before storing it. When the client requests the data, the server decrypts it and sends it back. All encryption/decryption happens on the server — the client always receives decrypted data. Los datos llegan al servidor (posiblemente por HTTPS). El servidor usa una data key para cifrar los datos antes de guardarlos. Cuando el cliente los solicita, el servidor los descifra y los envía de vuelta. Todo el cifrado/descifrado ocurre en el servidor — el cliente siempre recibe datos descifrados.

Client-Side Encryption Cifrado del Lado del Cliente

The client encrypts the data using its own data key before sending it. The server stores the encrypted blob and cannot decrypt it — we don't trust the server. The client must retain the data key to decrypt the data when retrieved. S3 SSE-C is an example: you provide the key per request. El cliente cifra los datos usando su propia data key antes de enviarlos. El servidor guarda el blob cifrado y no puede descifrarlo — no confiamos en el servidor. El cliente debe retener la data key para descifrar cuando recupera los datos. S3 SSE-C es un ejemplo: vos proveés la clave por cada request.

AWS KMS — Key Management Service AWS KMS — Key Management Service

KMS is the central encryption service of AWS. Any time you enable encryption on an AWS service — EBS, S3, RDS, SSM, Lambda env vars — it's almost certainly using KMS under the hood. AWS manages the key infrastructure; you control access via IAM and key policies. Every single use of a KMS key is audited in CloudTrail. KMS es el servicio de cifrado central de AWS. Cada vez que habilitás cifrado en un servicio de AWS — EBS, S3, RDS, SSM, variables de entorno de Lambda — casi con certeza está usando KMS internamente. AWS gestiona la infraestructura de claves; vos controlás el acceso via IAM y key policies. Cada uso de una clave KMS queda auditado en CloudTrail.

How Key Rotation Actually Works Cómo Funciona la Rotación Internamente

When KMS rotates a CMK, it does not delete the old key material. It keeps all previous versions internally so it can still decrypt data that was encrypted with them. From your perspective nothing changes — the Key ID stays the same, and your code doesn't need to be updated. Only new encryptions use the new material; existing ciphertexts are decrypted with whichever version encrypted them. Cuando KMS rota una CMK, no borra el material de clave anterior. Lo conserva internamente para poder seguir descifrando datos que fueron cifrados con versiones anteriores. Desde tu perspectiva nada cambia — el Key ID es el mismo y tu código no necesita actualizarse. Solo los nuevos cifrados usan el material nuevo; los ciphertexts existentes se descifran con la versión que los cifró.

For Imported CMKs (no automatic rotation), the pattern is to create a new key with new material, then update the alias to point to it. Your code never changes because it always references the alias: Para Imported CMKs (sin rotación automática), el patrón es crear una nueva clave con nuevo material y actualizar el alias para que apunte a ella. Tu código nunca cambia porque siempre referencia el alias:

alias/mi-clave  →  key-v1  (old material)

# After manual rotation
alias/mi-clave  →  key-v2  (new material)

# Your code — unchanged
kms.decrypt(KeyId="alias/mi-clave")  ✅ just works

AWS Managed Keys — The aws:ViaService Condition AWS Managed Keys — La condición aws:ViaService

AWS Managed Keys (like aws/ebs or aws/sqs) have a key policy that restricts usage to a specific AWS service via the aws:ViaService condition. This means the aws/ebs key can only be used by requests coming from the EC2 service — you cannot call kms:Decrypt on it directly from your Lambda or CLI. This is why, for custom encryption scenarios, you need your own Customer Managed Key. Las AWS Managed Keys (como aws/ebs o aws/sqs) tienen una key policy que restringe el uso a un servicio AWS específico mediante la condición aws:ViaService. Esto significa que la clave aws/ebs solo puede usarse desde solicitudes que vengan del servicio EC2 — no podés llamar kms:Decrypt sobre ella directamente desde Lambda o CLI. Por eso, para escenarios de cifrado personalizados, necesitás una Customer Managed Key propia.

KMS Keys Are Regional Las Claves KMS Son Regionales

A KMS key exists in one region only. To copy an encrypted EBS snapshot across regions, AWS must re-encrypt it using a different KMS key in the destination region. This happens automatically during the copy operation — you choose the destination key. Una clave KMS existe en una sola región. Para copiar un snapshot de EBS cifrado entre regiones, AWS debe re-cifrarlo usando una clave KMS diferente en la región destino. Esto ocurre automáticamente durante la copia — vos elegís la clave destino.

KMS Key Policies KMS Key Policies

Key policies control who can access a KMS key — similar to S3 bucket policies. The critical difference: if there is no key policy, nobody can access the key (not even root). There are two types: the default policy (allows the whole account via IAM) and custom policies (explicitly list users/roles — required for cross-account access). Las key policies controlan quién puede acceder a una clave KMS — similar a las bucket policies de S3. La diferencia crítica: si no hay key policy, nadie puede acceder a la clave (ni root). Hay dos tipos: la política por defecto (permite toda la cuenta via IAM) y políticas personalizadas (listan usuarios/roles explícitamente — requeridas para acceso cross-account).

KMS CLI — Encrypt, Decrypt & ReEncrypt KMS CLI — Encrypt, Decrypt y ReEncrypt

KMS operations can be performed directly from the CLI. The output is always Base64-encoded, so you need to decode it before saving as a binary file or reading as plaintext. Think of Base64 as just a transport format — it has nothing to do with the encryption itself. Las operaciones de KMS se pueden realizar directamente desde la CLI. La salida siempre viene en Base64, por lo que hay que decodificarla antes de guardarla como binario o leerla como texto. Base64 es solo un formato de transporte — no tiene nada que ver con el cifrado en sí. 

# Encrypt: send plaintext → get back CiphertextBlob (Base64)
aws kms encrypt \
  --key-id alias/tutorial \
  --plaintext fileb://secret.txt \
  --output text --query CiphertextBlob \
  | base64 --decode > secret.bin

# Decrypt: send ciphertext → get back Plaintext (Base64)
aws kms decrypt \
  --ciphertext-blob fileb://secret.bin \
  --output text --query Plaintext \
  | base64 --decode > secret-decrypted.txt

ReEncrypt — Change Key Without Exposing Plaintext ReEncrypt — Cambiar de Key Sin Exponer el Plaintext

kms:ReEncrypt lets KMS internally decrypt with key A and re-encrypt with key B — the plaintext never leaves KMS and never appears in your application. Requires kms:ReEncrypt* permission on both the source key (to decrypt) and the destination key (to encrypt). Typical use case: migrating data to a new CMK without exposing its contents. kms:ReEncrypt hace que KMS descifre internamente con la key A y vuelva a cifrar con la key B — el plaintext nunca sale de KMS ni aparece en tu aplicación. Requiere permiso kms:ReEncrypt* tanto en la key de origen (para descifrar) como en la de destino (para cifrar). Caso de uso típico: migrar datos a una nueva CMK sin exponer su contenido.

KMS Envelope Encryption & Key APIs KMS Envelope Encryption y APIs de Claves

The KMS Encrypt API has a hard limit of 4 KB. For anything larger, you need envelope encryption — a pattern where KMS generates a data key, you encrypt the file locally with that key, and store the encrypted file alongside the encrypted data key. This is the core technique behind the AWS Encryption SDK. La API Encrypt de KMS tiene un límite fijo de 4 KB. Para datos más grandes, necesitás envelope encryption — un patrón donde KMS genera una data key, vos cifrás el archivo localmente con esa clave, y guardás el archivo cifrado junto con la data key cifrada. Esta es la técnica central detrás del AWS Encryption SDK.

Envelope Encryption — Encrypt Flow Envelope Encryption — Flujo de Cifrado

The flow involves one KMS call to generate a data key, then all encryption happens client-side. The result is an "envelope" file: the encrypted big file wrapped together with the encrypted DEK. El flujo implica una llamada a KMS para generar una data key, luego todo el cifrado ocurre del lado del cliente. El resultado es un archivo "envelope": el archivo grande cifrado envuelto junto con el DEK cifrado.

Envelope Encryption — Decrypt Flow Envelope Encryption — Flujo de Descifrado

To decrypt, extract the encrypted DEK from the envelope and send it to KMS Decrypt (≤4 KB). KMS returns the plaintext DEK, which you then use locally to decrypt the file. Para descifrar, extraés el DEK cifrado del envelope y lo enviás a KMS Decrypt (≤4 KB). KMS devuelve el DEK en texto plano, que usás localmente para descifrar el archivo.

KMS Throttling, Lambda & S3 Integration KMS Throttling, Lambda y S3

KMS has per-region, per-account request quotas shared across all cryptographic operations. When you exceed them you get a ThrottlingException with 400 error code. The same quota is consumed by calls you make directly and by AWS services acting on your behalf (e.g. S3 encrypting every object with SSE-KMS). Two key integrations — Lambda env-var encryption and S3 Bucket Keys — show how KMS is used in practice and how to stay within quota and budget. KMS tiene cuotas de requests por región y cuenta, compartidas entre todas las operaciones criptográficas. Si las superás, obtenés una ThrottlingException con código de error 400. La misma cuota la consumen tanto tus llamadas directas como los servicios AWS que actúan en tu nombre (ej. S3 cifrando cada objeto con SSE-KMS). Dos integraciones clave — cifrado de env vars en Lambda y S3 Bucket Keys — muestran cómo se usa KMS en la práctica y cómo mantenerse dentro de la cuota y el presupuesto.

Lambda — Encrypting Environment Variables Lambda — Cifrar Variables de Entorno

Lambda environment variables are visible in plain text in the console by default. By enabling KMS encryption on them, the value is stored encrypted at rest. The Lambda function must then call kms:Decrypt at runtime to retrieve the plaintext value. The execution role needs explicit kms:Decrypt permission on the key ARN — without it you get an AccessDeniedException. Las variables de entorno de Lambda son visibles en texto plano en la consola por defecto. Al habilitar cifrado KMS, el valor se guarda cifrado en reposo. La función Lambda debe llamar a kms:Decrypt en tiempo de ejecución para obtener el valor en texto plano. El execution role necesita permiso explícito kms:Decrypt en el ARN de la clave — sin esto se obtiene AccessDeniedException.

EncryptionContext — KMS supports passing an optional key-value map as additional authenticated data (AAD). When provided during encryption, the exact same context must be supplied during decryption — otherwise KMS rejects the request. For Lambda env vars, the console-generated decrypt snippet uses LambdaFunctionName as context, tying the decryption to a specific function. This prevents one Lambda's encrypted value from being decrypted by a different Lambda. EncryptionContext — KMS soporta pasar un mapa clave-valor opcional como datos autenticados adicionales (AAD). Cuando se provee durante el cifrado, el mismo contexto debe suministrarse durante el descifrado — de lo contrario KMS rechaza la solicitud. Para las env vars de Lambda, el snippet de descifrado generado por la consola usa LambdaFunctionName como contexto, atando el descifrado a una función específica. Esto evita que el valor cifrado de una Lambda sea descifrado por otra Lambda diferente.

KMS Key Policies & CloudHSM KMS Key Policies y CloudHSM

Key policies are the primary access control mechanism for KMS keys — they work like S3 bucket policies but with one critical difference: without a key policy, nobody can use the key, not even the account root. CloudHSM is the alternative to KMS when you need to physically own the encryption hardware, achieve FIPS 140-2 Level 3 compliance, or manage keys completely independently from AWS. Las key policies son el mecanismo principal de control de acceso para claves KMS — funcionan como las bucket policies de S3 pero con una diferencia crítica: sin key policy, nadie puede usar la clave, ni siquiera el root de la cuenta. CloudHSM es la alternativa a KMS cuando necesitás poseer físicamente el hardware de cifrado, alcanzar cumplimiento FIPS 140-2 Level 3, o gestionar claves completamente independiente de AWS.

CloudHSM vs KMS CloudHSM vs KMS

CloudHSM provisions dedicated hardware (Hardware Security Module) in AWS. You manage the encryption keys entirely — AWS cannot access them. The device is tamper-resistant (FIPS 140-2 Level 3). High availability is achieved by clustering multiple HSM devices across AZs. CloudHSM integrates with KMS via a custom key store, so services like EBS and S3 can use KMS APIs while the actual key operations run on your HSM cluster. CloudHSM aprovisiona hardware dedicado (Hardware Security Module) en AWS. Vos gestionás las claves de cifrado completamente — AWS no puede accederlas. El dispositivo es resistente a manipulaciones (FIPS 140-2 Level 3). La alta disponibilidad se logra agrupando múltiples dispositivos HSM en distintas AZs. CloudHSM se integra con KMS via un custom key store, para que servicios como EBS y S3 usen APIs KMS mientras las operaciones de clave reales se ejecutan en tu clúster HSM.

Tricky Quiz Questions Preguntas Tricky del Quiz

30.3 — An external team needs to encrypt data that only your app can decrypt. What type of KMS key? 30.3 — Un equipo externo necesita cifrar datos que solo tu app puede descifrar. ¿Qué tipo de KMS key?

✅ Asymmetric CMK ✅ Asymmetric CMK

Imported CMK is about where the key material comes from (outside AWS), not about who can encrypt. The correct answer is Asymmetric CMK — the public key can be downloaded and used outside AWS to encrypt; only your app can call kms:Decrypt with the private key that never leaves KMS. Imported CMK tiene que ver con el origen del material de clave (fuera de AWS), no con quién puede cifrar. La correcta es Asymmetric CMK — la clave pública se descarga y el equipo externo la usa para cifrar; solo tu app puede llamar kms:Decrypt con la clave privada que nunca sale de KMS.

Quiz 27 — Do you need to create your own KMS keys to use encryption in EBS, S3, RDS? Quiz 27 — ¿Necesitás crear tus propias KMS keys para usar encriptación en EBS, S3, RDS?

✅ False ✅ False

AWS provides AWS Managed Keys (aws/s3, aws/ebs, aws/rds…) created automatically when you enable encryption on a service. You don't need to create your own CMKs — they're optional for extra control (rotation, key policies, cross-account). The trap: assuming you always need a Customer Managed Key. AWS provee AWS Managed Keys (aws/s3, aws/ebs, aws/rds…) que se crean automáticamente al habilitar encriptación en un servicio. No hace falta crear tus propias CMKs — son opcionales para mayor control (rotación, key policies, cross-account). La trampa: asumir que siempre necesitás una Customer Managed Key.

Quiz 27 — You shared an AMI with an encrypted EBS snapshot (CMK) with another AWS account, but they still can't use it. What's missing? Quiz 27 — Compartiste un AMI con snapshot EBS encriptado con CMK con otra cuenta AWS, pero no pueden usarlo. ¿Qué falta?

✅ Share the KMS CMK with the other account (update the key policy) ✅ Compartir el KMS CMK con la otra cuenta (modificar la key policy)

Sharing the AMI is not enough — the EBS snapshot is encrypted with your CMK, and the other account has no access to it. Update the KMS key policy to grant access. The CMK stays in your account; the other account just gets permission to use it. Don't confuse with cross-region: copying a snapshot across regions DOES require a different KMS key in the destination region. Cross-account (same region) only needs key policy access. Compartir el AMI no alcanza — el snapshot EBS está encriptado con tu CMK y la otra cuenta no tiene acceso. Hay que actualizar la key policy del CMK para incluir el ID de la otra cuenta.
