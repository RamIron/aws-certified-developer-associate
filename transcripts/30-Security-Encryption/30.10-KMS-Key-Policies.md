# 30.10 — KMS Key Policies & Principals

## Key Policy Recap

- Without a key policy → **no one** can access the key
- Default policy: allows all principals in the account (IAM policies then control access)
- Custom policy: explicitly names users/roles — needed for cross-account and fine-grained control

## Valid Principal Types in KMS Key Policies

| Principal type | Example | Notes |
|---|---|---|
| Account / root | `arn:aws:iam::123456789012:root` | Allows all principals in account (IAM kicks in) |
| IAM Role | `arn:aws:iam::123456789012:role/MyRole` | Specific role |
| IAM Role Session | `arn:aws:sts::123456789012:assumed-role/MyRole/session` | Assumed role or Cognito/SAML federated |
| IAM User | `arn:aws:iam::123456789012:user/alice` | Specific user |
| Federated User Session | `arn:aws:sts::123456789012:federated-user/alice` | User federation |
| AWS Service | `logs.eu-west-2.amazonaws.com` | Allow a service to use the key |
| Everyone | `*` or `AWS: *` | Full open access |

## Example: Allowing CloudWatch Logs to Use a Key

The `Via Service` condition is set per service. For CloudWatch Logs, you need to add the service as a principal in the key policy:

```json
{
  "Effect": "Allow",
  "Principal": {
    "Service": "logs.eu-west-2.amazonaws.com"
  },
  "Action": ["kms:Encrypt", "kms:Decrypt", "kms:ReEncrypt*",
              "kms:GenerateDataKey*", "kms:Describe*"],
  "Resource": "*"
}
```

Without this → `AccessDeniedException` even if you own the key.

## Explicit Principal = No Extra IAM Policy Needed

If a federated user or specific role is **explicitly listed** in the key policy,  
they do **not** need an additional IAM policy to use the key.  
The key policy alone is sufficient.
