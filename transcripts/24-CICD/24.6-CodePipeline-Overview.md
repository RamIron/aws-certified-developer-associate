# 24.6 - CodePipeline Overview

## Key Concepts

### 1. What is CodePipeline?
- **Visual workflow tool** to orchestrate CI/CD within AWS
- Does NOT build or deploy itself — it **orchestrates** other services
- You define stages, each stage has sequential and/or parallel actions

### 2. Stage Types & Supported Services
| Stage | Supported Services |
|---|---|
| Source | CodeCommit, ECR, S3, GitHub, Bitbucket |
| Build | CodeBuild, Jenkins, CloudBees, TeamCity |
| Test | CodeBuild, AWS Device Farm, 3rd party tools |
| Deploy | CodeDeploy, Elastic Beanstalk, CloudFormation, ECS, S3 |
| Invoke | Lambda function, Step Functions |

- Stages can have **manual approval** actions (e.g. approve before deploying to prod)

### 3. Artifacts & S3
- Each stage produces **artifacts** (output files/packages)
- Artifacts are stored in **S3** and passed to the next stage
- This is why CodeBuild doesn't need direct access to CodeCommit — CodePipeline pulls the code and pushes it to CodeBuild via S3

```
CodeCommit → [artifact] → S3 → CodeBuild → [artifact] → S3 → CodeDeploy
                    CodePipeline orchestrates all of this
```

### 4. Troubleshooting
| Problem | Tool / Solution |
|---|---|
| Monitor stage/action execution changes | CloudWatch Events / EventBridge |
| Failed pipeline notifications | EventBridge → SNS email |
| Stage failure info | Visible in the CodePipeline console |
| Can't invoke CodeBuild / pull from CodeCommit | Check **IAM service role** of CodePipeline |
| Audit API calls | **CloudTrail** |

## Exam Tips
- CodePipeline = **orchestrator**, not builder/deployer
- Artifacts are passed between stages via **S3**
- Pipeline failures → check **IAM service role** permissions
- Audit API calls → **CloudTrail**
- Monitoring pipeline events → **EventBridge**
- Manual approval can be added at **any stage**
