CICD OverviewVisión General de CICD

Everything done manually so far in the course — clicking the console, running CLI commands, deploying via Beanstalk — is slow and error-prone at scale. CICD automates the full path from a code push to a production deployment, adding both speed (deploy constantly, not once every 3 months) and safety (nothing ships untested). You can also define multiple stages (dev → test → staging → prod) with optional manual approvals before hitting production.Todo lo hecho manualmente hasta ahora en el curso — consola, CLI, Beanstalk a mano — es lento y propenso a errores a escala. CICD automatiza el camino completo desde un push de código hasta producción, agregando velocidad (deployar constantemente, no cada 3 meses) y seguridad (nada llega a producción sin testear). También podés definir múltiples stages (dev → test → staging → prod) con aprobaciones manuales opcionales antes de producción.

CI vs CDCI vs CD

The two halves of the pipeline have distinct responsibilities. CI (Continuous Integration) is about the left side — every code push triggers an automatic build and test cycle, giving developers fast feedback without testing on their own machine. CD (Continuous Delivery) extends that — every green build is automatically deployed to application servers, shifting the team away from rare, risky big-bang releases toward small, frequent, automated ones.Las dos mitades del pipeline tienen responsabilidades distintas. CI (Integración Continua) es el lado izquierdo — cada push dispara un ciclo automático de build y test, dando feedback rápido sin necesidad de testear en la máquina local. CD (Entrega Continua) lo extiende — cada build verde se deploya automáticamente, alejando al equipo de releases grandes y riesgosas hacia releases pequeñas, frecuentes y automatizadas.

You use the exact same git push / git pull / git clone commands as any Git workflow — the difference is that your code stays entirely within your AWS VPC, never leaving the AWS cloud. CodePipeline is the orchestrator of your CI/CD workflow. It doesn't build or deploy anything itself — it connects and sequences the services that do. You define a pipeline as a series of stages, each stage containing one or more actions that can run sequentially or in parallel. A manual approval action can be inserted at any stage. CodePipeline es el orquestador de tu flujo CI/CD. No buildea ni deploya por sí mismo — conecta y secuencia los servicios que lo hacen. Definís un pipeline como una serie de stages, cada uno con una o más acciones que pueden correr en secuencia o en paralelo. Se puede insertar una aprobación manual en cualquier stage.

Artifacts & S3 — How Stages Talk to Each OtherArtifacts y S3 — Cómo se Comunican los Stages

Each stage that produces output generates an artifact — a package of files stored in S3. The next stage picks it up from S3 as its input. Stages never communicate directly with each other; S3 is always the intermediary. The final Deploy stage is a consumer only — it receives the build artifact and deploys it, but produces no artifact of its own. CodeBuildCodeBuild

CodeBuild is a fully managed build service. You point it at source code and it spins up a Docker container, runs your build and test instructions, and produces output artifacts. AWS provides pre-built Docker images for common runtimes (Java, Python, Node.js, Go, Ruby, .NET Core, Android, PHP) so you don't need to know Docker for those. For anything else, you extend a Docker image yourself. CodeBuild can be triggered standalone or invoked by CodePipeline as its Build stage. CodeBuild es un servicio de build completamente gestionado. Apuntás al código fuente y levanta un contenedor Docker, ejecuta las instrucciones de build y test, y produce artifacts de salida. AWS provee imágenes Docker pre-construidas para los runtimes más comunes (Java, Python, Node.js, Go, Ruby, .NET Core, Android, PHP), por lo que no necesitás saber Docker para esos casos. Para cualquier otro entorno, extendés una imagen Docker propia. CodeBuild puede ejecutarse de forma standalone o ser invocado por CodePipeline como su stage de Build.

CodeArtifactCodeArtifact

CodeArtifact is a managed artifact repository — it stores the software packages your code depends on. Instead of developers fetching directly from public registries (npm, PyPI, Maven Central, NuGet), they point their package manager at CodeArtifact, which acts as a proxy and cache. Packages are fetched once and stored; if the public registry goes down, builds keep working. CodeArtifact es un repositorio de artefactos gestionado — almacena los paquetes de software de los que depende tu código. En lugar de que los desarrolladores busquen directamente en registros públicos (npm, PyPI, Maven Central, NuGet), apuntan su gestor de paquetes a CodeArtifact, que actúa como proxy y caché. Los paquetes se obtienen una vez y se almacenan; si el registro público cae, las builds siguen funcionando.

Q: To prevent developers from committing secret credentials to CodeCommit, you want to automatically trigger code analysis after each commit. How? Q: Para prevenir que los developers hagan commit de credenciales secretas en CodeCommit, querés disparar análisis de código automáticamente tras cada commit. ¿Cómo?

✗ Setup AWS CloudWatch Events in CodeCommitConfigurar AWS CloudWatch Events en CodeCommit

✅ Setup AWS SNS / Lambda integration in CodeCommitConfigurar integración de AWS SNS / Lambda en CodeCommit

CodeCommit has native repository triggers that can directly invoke a Lambda function or send to an SNS topic on every push — without going through EventBridge. That Lambda then runs the code analysis (e.g. scans for secrets). CloudWatch Events is used for notifications/monitoring, not for direct trigger-on-commit workflows. CodeCommit tiene repository triggers nativos que pueden invocar directamente una función Lambda o enviar a un topic SNS en cada push — sin pasar por EventBridge. Ese Lambda luego corre el análisis (p.ej. escanea credenciales). CloudWatch Events se usa para notificaciones/monitoreo, no para workflows de trigger-on-commit directos.

SNS alone doesn't know when CodePipeline fails — you need a CloudWatch Event Rule to detect the pipeline FAILED state change first. That rule then triggers the notification (via SNS/email).
