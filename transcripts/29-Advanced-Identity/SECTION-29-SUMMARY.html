AWS Security Token Service (STS) AWS Security Token Service (STS)

STS issues temporary security credentials — valid for up to one hour — that allow users, applications, and services to access AWS resources without needing permanent IAM users or long-term access keys. The core pattern is: call an STS API → receive temporary credentials → use those credentials to act as an IAM role or federated identity. STS emite credenciales de seguridad temporales — válidas hasta una hora — que permiten a usuarios, aplicaciones y servicios acceder a recursos de AWS sin necesitar usuarios IAM permanentes ni access keys de largo plazo. El patrón central es: llamar a una API de STS → recibir credenciales temporales → usarlas para actuar como un rol IAM o identidad federada.

Advanced IAM Policies Políticas IAM Avanzadas

This card covers three IAM concepts that are easy to get wrong on the exam: how policy evaluation actually works (deny vs allow precedence), how IAM and S3 bucket policies interact (union evaluation), and two techniques for writing more maintainable policies (dynamic variables and managed vs inline). Esta card cubre tres conceptos de IAM que son fáciles de confundir en el examen: cómo funciona realmente la evaluación de políticas (precedencia deny vs allow), cómo interactúan las políticas IAM y de bucket S3 (evaluación por unión), y dos técnicas para políticas más mantenibles (variables dinámicas y managed vs inline).

1. Policy Evaluation Model 1. Modelo de Evaluación de Políticas

IAM evaluates all applicable policies for a request in this order. An explicit deny always terminates the evaluation immediately — no allow can override it. IAM evalúa todas las políticas aplicables a un request en este orden. Un deny explícito siempre termina la evaluación de inmediato — ningún allow puede sobreescribirlo.

2. IAM Policy + S3 Bucket Policy = Union 2. Política IAM + Política de Bucket S3 = Unión

When an IAM principal takes action on S3, AWS evaluates the union of the IAM policy and the S3 bucket policy together. An explicit deny in either one wins. An allow in either one is sufficient (unless countered by a deny). Cuando un principal IAM actúa sobre S3, AWS evalúa la unión de la política IAM y la política de bucket S3 juntas. Un deny explícito en cualquiera de las dos gana. Un allow en cualquiera es suficiente (salvo que lo contradiga un deny).

3. Dynamic IAM Policies 3. Políticas IAM Dinámicas

Instead of creating one policy per user (which doesn't scale), you use policy variables that are resolved at runtime. The most common variable is ${aws:username}, which is replaced by the caller's IAM username when the policy is evaluated. En lugar de crear una política por usuario (lo cual no escala), se usan variables de política que se resuelven en tiempo de ejecución. La variable más común es ${aws:username}, que se reemplaza por el nombre de usuario IAM del llamador al evaluar la política.

Example:Ejemplo: "arn:aws:s3:::my-bucket/home/${aws:username}/*"
One policy → all users → each user can only access their own /home/username/ folder. Una política → todos los usuarios → cada usuario solo accede a su propia carpeta /home/username/.

IAM PassRole IAM PassRole

Every time you assign an IAM role to an AWS service — creating an EC2 instance with a role, deploying a Lambda with an execution role, configuring CodePipeline — you are passing that role. Passing a role requires a specific IAM permission: iam:PassRole. Without it, the assignment is denied, even if you have full admin access to EC2 or Lambda. Cada vez que asignás un rol IAM a un servicio de AWS — creando una instancia EC2 con rol, desplegando una Lambda con rol de ejecución, configurando CodePipeline — estás pasando ese rol. Pasar un rol requiere un permiso IAM específico: iam:PassRole. Sin él, la asignación se deniega, aunque tengas acceso total a EC2 o Lambda.

Required Permissions Permisos Necesarios

To pass a role to a service, your user needs two permissions. Note that iam:PassRole can be scoped to a specific role ARN — you don't have to allow passing any role. Para pasar un rol a un servicio, tu usuario necesita dos permisos. Notá que iam:PassRole puede restringirse a un ARN de rol específico — no tenés que permitir pasar cualquier rol.

AWS Directory Services AWS Directory Services

Microsoft Active Directory (AD) is the Windows-world identity system — a database of users, computers, and groups managed by a Domain Controller. All Windows machines on the network authenticate against it. AWS Directory Services gives you three ways to bring AD into AWS, each with different trade-offs between where users live and whether an on-premise AD is required. Microsoft Active Directory (AD) es el sistema de identidades del mundo Windows — una base de datos de usuarios, computadoras y grupos gestionada por un Domain Controller. Todas las máquinas Windows de la red se autentican contra él. AWS Directory Services ofrece tres formas de llevar AD a AWS, cada una con distintos trade-offs entre dónde viven los usuarios y si se requiere un AD on-premise.

What is Active Directory? ¿Qué es Active Directory?

A Domain Controller holds all user accounts. Every Windows machine in the network connects to it — when you log in to any machine, it validates your credentials centrally against the DC. A collection of AD trees is called a forest. Un Domain Controller almacena todas las cuentas de usuario. Cada máquina Windows de la red se conecta a él — cuando iniciás sesión en cualquier máquina, valida tus credenciales centralmente contra el DC. Una colección de árboles AD se llama forest.

Tricky Quiz Questions Preguntas Tricky del Quiz

You have an on-premises AD. You need to create another AD in AWS and establish a trust relationship with the on-premises one. Which service? Tenés un AD on-premise. Necesitás crear otro AD en AWS y establecer una trust relationship con el on-premise. ¿Qué servicio?

✅ AWS Managed Microsoft AD

The trap is AD Connector — "trust relationship" sounds like a connection to on-premise, which points to AD Connector. But a trust relationship requires TWO ADs. AD Connector is not an AD, it's a proxy — it creates nothing in AWS. AWS Managed Microsoft AD actually creates a real AD in AWS and supports bidirectional trust with on-premise. La trampa es AD Connector — "trust relationship" suena a conexión con on-premise, lo que apunta a AD Connector. Pero una trust relationship requiere DOS ADs. AD Connector no es un AD, es un proxy — no crea nada en AWS. AWS Managed Microsoft AD sí crea un AD real en AWS y soporta trust bidireccional con on-premise.

An EC2 instance had an IAM role with read/write to S3. The role was removed. Writes stopped but reads still work. Why? Una EC2 tenía un IAM role con read/write a S3. Se removió el rol. Las escrituras fallaron pero las lecturas siguen funcionando. ¿Por qué?

✅ The S3 bucket policy still authorizes reads✅ La S3 bucket policy sigue autorizando lecturas

This is union evaluation in action. Even with no IAM role on the EC2, if the S3 bucket policy explicitly allows reads for that instance, the reads still go through. The write permission only existed in the IAM role — once removed, writes fail. Reads survive because the bucket policy covers them independently. Esto es la evaluación por unión en acción. Aunque la EC2 no tenga IAM role, si la S3 bucket policy permite lecturas explícitamente, las lecturas funcionan igual. El permiso de escritura solo existía en el IAM role — al removerse, las escrituras fallan. Las lecturas sobreviven porque la bucket policy las cubre de forma independiente.

What does this policy allow? (ec2:* on *, iam:PassRole on arn:aws:iam:::role/RDS-*) ¿Qué permite esta política? (ec2:* en *, iam:PassRole en arn:aws:iam:::role/RDS-*)

✅ It allows you to assign RDS full access to EC2 instances✅ Permite asignar acceso completo a RDS a instancias EC2

The trap is the wildcard: arn:aws:iam:::role/RDS-* restricts PassRole to only roles whose name starts with RDS-. Those are RDS-access roles — so EC2 can only be assigned RDS roles, not any role. The policy is NOT about assigning roles to RDS instances — it's about assigning RDS-prefixed roles TO EC2. La trampa es el wildcard: arn:aws:iam:::role/RDS-* restringe PassRole a roles cuyo nombre empieza con RDS-. Esos son roles de acceso a RDS — entonces EC2 solo puede recibir roles de RDS, no cualquier rol. La política NO es sobre asignar roles a instancias RDS — es sobre asignar roles con prefijo RDS A EC2.

Which two permissions does a developer need to pass a role to an AWS service? ¿Qué dos permisos necesita un desarrollador para pasar un rol a un servicio AWS?

✅ iam:PassRole + iam:GetRole

The trap is sts:AssumeRole — that's what the service uses internally to take on the role, not what the developer needs. The developer passes the role (iam:PassRole) and can view it (iam:GetRole). The service assumes it (sts:AssumeRole). La trampa es sts:AssumeRole — eso lo usa el servicio internamente para asumir el rol, no el desarrollador. El desarrollador pasa el rol (iam:PassRole) y puede verlo (iam:GetRole). El servicio lo asume (sts:AssumeRole).
