Amazon SQS — Standard QueueAmazon SQS — Cola Estandar

SQS is a fully managed message queuing service that decouples producers from consumers — the producer doesn't need to know who will process the message or when. A producer sends messages to a queue; consumers poll the queue, process each message, and then explicitly delete it to confirm processing. The queue acts as a buffer: if the consumer is slow or temporarily down, messages wait safely in the queue. SQS es un servicio de colas de mensajes totalmente gestionado que desacopla productores de consumidores. Un productor envia mensajes a la cola; los consumidores hacen poll, procesan cada mensaje y luego lo eliminan explicitamente para confirmar el procesamiento. La cola actua como buffer: si el consumidor es lento o no esta disponible, los mensajes esperan de forma segura.

Standard queues offer unlimited throughput (no cap on how many messages per second you can send or receive) and at-least-once delivery — meaning the same message can arrive more than once (your consumer must handle duplicates). Ordering is best-effort, not guaranteed. Las colas Standard ofrecen throughput ilimitado (sin limite de mensajes por segundo que podés enviar o recibir) y entrega al-menos-una-vez — el mismo mensaje puede llegar mas de una vez (el consumidor debe manejar duplicados). El orden es de mejor esfuerzo, no garantizado.

SQS Security & Access PoliciesSeguridad y Politicas de Acceso SQS

SQS has two independent layers of security: encryption (protecting the data itself) and access control (who can send or receive). Understanding which tool handles each scenario is a common exam topic. SQS tiene dos capas independientes de seguridad: encriptacion (proteger los datos) y control de acceso (quien puede enviar o recibir). Saber que herramienta aplica a cada escenario es un tema comun en el examen.

EncryptionEncriptacion

SQS supports three encryption approaches depending on where and who protects the data: in-flight (data moving over the network), at-rest via AWS (data stored on disk, managed by KMS), and client-side (data encrypted by your own application before it even reaches SQS — AWS never sees the plaintext). SQS soporta tres enfoques de encriptacion segun donde y quien protege los datos: en transito (datos viajando por la red), en reposo via AWS (datos en disco, gestionados por KMS), y del lado del cliente (datos encriptados por tu propia aplicacion antes de llegar a SQS — AWS nunca ve el texto plano).

SQS Advanced ConceptsConceptos Avanzados SQS

Beyond the basics, SQS provides several mechanisms to handle failure, large payloads, and high-volume polling efficiently. These are key exam topics because they represent real-world operational decisions. Mas alla de lo basico, SQS ofrece mecanismos para manejar fallos, payloads grandes y polling de alto volumen de forma eficiente. Son temas clave del examen porque representan decisiones operacionales del mundo real.

Dead Letter Queue (DLQ)Cola de Mensajes Fallidos (DLQ)

A DLQ is a safety net for poison-pill messages — messages that consistently fail processing (e.g., malformed data that always crashes the consumer). Instead of blocking the queue forever, SQS moves them to a separate queue after a configurable number of failures, where they can be inspected without impacting the main flow. Una DLQ es una red de seguridad para mensajes "poison-pill" — mensajes que fallan consistentemente (ej. datos malformados que siempre crashean el consumidor). En lugar de bloquear la cola indefinidamente, SQS los mueve a una cola separada tras un numero configurable de fallos, donde pueden inspeccionarse sin impactar el flujo principal.

After MaximumReceives threshold is exceeded, message moves to DLQ for debugging. DLQ type must match source (FIFO→FIFO, Standard→Standard). Set retention to 14 days. Use Redrive to Source to reprocess after fixing consumer. Cuando se excede el umbral MaximumReceives, el mensaje se mueve a la DLQ para depuracion. El tipo de DLQ debe coincidir (FIFO→FIFO, Standard→Standard). Retencion: 14 dias. Usar Redrive to Source para reprocesar despues de arreglar el consumidor.

Warning: If a message expires in the source queue before reaching MaximumReceives, it's lost forever — never reaches the DLQ. Atencion: Si un mensaje expira en la cola fuente antes de alcanzar MaximumReceives, se pierde para siempre — nunca llega a la DLQ.

Delay QueueCola con Retraso

A Delay Queue makes messages invisible to consumers for a configurable time after they're sent. This is useful when the consumer needs to wait for a related operation to complete first — for example, delaying an order confirmation email to give the payment system time to settle. The delay can be set at the queue level (applies to all messages) or overridden per message using DelaySeconds. Max delay is 15 minutes; default is 0s. Una Delay Queue hace que los mensajes sean invisibles para los consumidores durante un tiempo configurable tras ser enviados. Es util cuando el consumidor necesita esperar a que una operacion relacionada termine primero — por ejemplo, retrasar un email de confirmacion de pedido para dar tiempo al sistema de pagos. El retraso puede configurarse a nivel de cola (aplica a todos) o sobreescribirse por mensaje con DelaySeconds. Max: 15 minutos; por defecto: 0s.

Long PollingLong Polling

Consumer waits for messages if queue is empty. Range: 1–20 seconds (20 recommended). Reduces API calls and cost. Enable via ReceiveMessageWaitTimeSeconds or queue-level setting. El consumidor espera mensajes si la cola esta vacia. Rango: 1–20 segundos (20 recomendado). Reduce llamadas API y costo. Activar via ReceiveMessageWaitTimeSeconds o a nivel de cola.

SQS Extended ClientCliente Extendido SQS

SQS has a hard 1 MiB limit per message. For larger payloads (e.g., images, documents), the SQS Extended Client Library (Java) transparently uploads the full payload to S3 and sends only a small metadata pointer (the S3 reference) through SQS. The consumer uses the same library to automatically retrieve the full payload from S3. SQS tiene un limite estricto de 1 MiB por mensaje. Para payloads mas grandes (ej. imagenes, documentos), la SQS Extended Client Library (Java) sube el payload completo a S3 y envia solo un puntero de metadata (la referencia S3) por SQS. El consumidor usa la misma libreria para recuperar automaticamente el payload desde S3.

SQS FIFO QueuesColas FIFO de SQS

FIFO (First-In-First-Out) queues guarantee that messages are processed in the exact order they were sent and that each message is processed exactly once — solving both problems of Standard queues (no guaranteed order, possible duplicates). Use FIFO when order matters: financial transactions, event sequencing, or any workflow where step B must happen after step A. The trade-off is lower throughput. The queue name must end with .fifo. Las colas FIFO garantizan que los mensajes se procesen en el orden exacto en que fueron enviados y que cada mensaje se procese exactamente una vez — resolviendo ambos problemas de las colas Standard (sin orden garantizado, posibles duplicados). Usar FIFO cuando el orden importa: transacciones financieras, secuenciacion de eventos, o cualquier flujo donde B debe ocurrir despues de A. El trade-off es menor throughput. El nombre debe terminar en .fifo.

Amazon SNS — Pub/SubAmazon SNS — Pub/Sub

SNS follows the Publish/Subscribe model: one producer publishes to a topic and SNS immediately pushes a copy of the message to every subscriber — no polling required on the consumer's side. This is the key difference from SQS: SNS actively fans out to many targets at once, while SQS passively holds messages for one consumer to pull. SNS sigue el modelo Publish/Subscribe: un productor publica a un topic y SNS inmediatamente hace push de una copia del mensaje a cada suscriptor — sin polling del lado del consumidor. Esta es la diferencia clave con SQS: SNS distribuye activamente a muchos destinos, mientras que SQS retiene pasivamente mensajes para que un consumidor los jale.

Critical: SNS data is not persisted. If a subscriber is down or no subscriber is configured when the message arrives, that message is lost forever. For durability, combine with SQS (fan-out pattern). Critico: los datos de SNS no persisten. Si un suscriptor esta caido o no hay suscriptor configurado cuando llega el mensaje, ese mensaje se pierde para siempre. Para durabilidad, combinar con SQS (patron fan-out).

SNS FIFO TopicsTopics FIFO de SNS

SNS FIFO topics add ordering and deduplication guarantees to the pub/sub model — messages are delivered to subscribers in the order they were published. However, because ordered delivery requires synchronous coordination, the only supported subscribers are SQS queues (Standard or FIFO). Lambda, Email, HTTP/S, and SMS are not supported as subscribers to FIFO topics. Orden + dedup. Suscriptores: solo colas SQS (Standard y FIFO). No Lambda, Email, HTTP.

Message FilteringFiltrado de Mensajes

By default, every subscriber to a topic receives every message. Message filtering lets each subscription define a JSON filter policy so it only receives messages that match certain attributes — for example, an SQS queue for "orders" only receiving messages where type = "order". The filter is applied at the subscription level, not the topic level. A subscription with no filter policy receives all messages. Politica de filtro JSON en la suscripcion (no en el topic). Sin filtro = recibe todos los mensajes.

SNS + SQS Fan Out PatternPatron Fan Out SNS + SQS

The fan-out pattern solves a fundamental problem: how to send the same event to multiple independent consumers without any of them depending on each other. Instead of sending one message directly to one queue, the producer publishes once to an SNS topic. Each downstream team/service subscribes with its own SQS queue — giving each one an independent, durable copy to process at its own pace. This is fully decoupled: adding a new consumer means just adding a new SQS subscription, with no change to the producer. El patron fan-out resuelve un problema fundamental: como enviar el mismo evento a multiples consumidores independientes sin que ninguno dependa de otro. En lugar de enviar un mensaje directamente a una cola, el productor publica una sola vez a un topic SNS. Cada equipo/servicio suscribe con su propia cola SQS — dando a cada uno una copia independiente y duradera para procesar a su ritmo. Es completamente desacoplado: agregar un nuevo consumidor solo requiere agregar una nueva suscripcion SQS, sin cambios en el productor.

S3 event limitation: One rule per event type + prefix. To send same event to multiple destinations, use fan out: S3 → SNS → multiple SQS queues. Limitacion S3: Una regla por tipo de evento + prefijo. Para enviar el mismo evento a multiples destinos, usar fan out: S3 → SNS → multiples colas SQS.

SNS → KDF → S3 for persisting/archiving all messages flowing through a topic. SNS → KDF → S3 para persistir/archivar todos los mensajes que fluyen por un topic.

Kinesis Data StreamsKinesis Data Streams

Kinesis Data Streams (KDS) is designed for ingesting and storing high-volume streaming data in real time — think clickstreams, IoT sensor readings, application logs, or financial transactions arriving continuously. Unlike SQS, data is immutable (not deleted after consumption) and can be replayed by rewinding to any point within the retention window. Multiple independent consumers can read the same stream simultaneously, each at their own position. Kinesis Data Streams (KDS) esta disenado para ingestar y almacenar datos de streaming de alto volumen en tiempo real — clickstreams, sensores IoT, logs de aplicaciones o transacciones financieras llegando continuamente. A diferencia de SQS, los datos son inmutables (no se eliminan tras el consumo) y pueden reprocessarse volviendo a cualquier punto dentro de la ventana de retencion. Multiples consumidores independientes pueden leer el mismo stream simultaneamente, cada uno en su propia posicion.

What is a Shard?¿Que es un Shard?

A stream is divided into shards — the basic unit of capacity. Each shard handles 1 MB/s write and 2 MB/s read independently. You provision the number of shards you need; more shards = more throughput. Records are assigned to shards using a partition key: all records with the same partition key always go to the same shard, which is how ordering is preserved (records within a shard are strictly ordered). Un stream se divide en shards — la unidad basica de capacidad. Cada shard maneja 1 MB/s de escritura y 2 MB/s de lectura de forma independiente. Se provisiona el numero de shards necesarios; mas shards = mas throughput. Los registros se asignan a shards usando una partition key: todos los registros con la misma partition key siempre van al mismo shard, que es como se preserva el orden (los registros dentro de un shard estan estrictamente ordenados).

Capacity Modes & Scaling Modos de Capacidad y Escalado

KDS offers two capacity modes that determine how throughput is provisioned and how you scale when traffic grows. The example 1 → 2 → 4 → 8 illustrates the rule starting from 1 shard, but the rule applies to any starting number: if you have 6 shards, you can go to 12, then 24, etc. — you just can't more than double in a single operation. KDS ofrece dos modos de capacidad que determinan como se provisiona el throughput y como se escala cuando crece el trafico. El ejemplo 1 → 2 → 4 → 8 ilustra la regla arrancando de 1 shard, pero aplica a cualquier punto de partida: si tenes 6 shards, podes ir a 12, luego a 24, etc. — simplemente no podes mas que duplicar en una sola operacion.

Provisioned mode: You manually set the number of shards upfront and pay per shard per hour. There are two resharding operations:
• Shard Splitting — divides one shard into two, increasing capacity. Each split operation can at most double the total count (1 → 2 → 4 → 8…).
• Shard Merging — combines two adjacent shards into one, decreasing capacity and cost when traffic drops.
There's no shortcut to jump to any arbitrary number in one step.

On-Demand mode: No upfront capacity decisions. KDS monitors your throughput and auto-scales based on peak usage from the past 30 days. Default capacity: 4 MB/s in. You pay per GB of data processed instead of per shard — simpler for unpredictable workloads. Modo Provisioned: Vos definís la cantidad de shards de antemano y pagás por shard por hora. Hay dos operaciones de resharding:
• Shard Splitting — divide un shard en dos, aumentando la capacidad. Cada operacion puede como máximo duplicar el total (1 → 2 → 4 → 8…).
• Shard Merging — combina dos shards adyacentes en uno, reduciendo capacidad y costo cuando baja el tráfico.
No hay forma de saltar directamente a cualquier número en un solo paso.

Modo On-Demand: Sin decisiones de capacidad de antemano. KDS monitorea tu throughput y escala automaticamente basandose en el pico de uso de los ultimos 30 dias. Capacidad por defecto: 4 MB/s entrada. Se paga por GB de datos procesados en lugar de por shard — mas simple para cargas de trabajo impredecibles.

KPL & KCL — Producer & Consumer Libraries KPL & KCL — Librerias de Producer y Consumer

AWS provides two official libraries that abstract the low-level Kinesis API for common producer and consumer patterns. AWS provee dos librerias oficiales que abstraen la API de bajo nivel de Kinesis para patrones comunes de producer y consumer.

KPL (Kinesis Producer Library): A Java library that optimizes writes by batching multiple records into a single API call (aggregation), maximizing shard throughput and reducing cost. Use it when you control the producer code.

KCL (Kinesis Client Library): A library that simplifies building consumers — it handles shard enumeration, checkpointing (tracking which records were already processed), and load balancing across multiple consumer instances automatically. KPL (Kinesis Producer Library): Libreria Java que optimiza escrituras agrupando (batching) multiples registros en una sola llamada API (agregacion), maximizando el throughput del shard y reduciendo costos. Usarla cuando controlas el codigo del productor.

KCL (Kinesis Client Library): Libreria que simplifica la construccion de consumidores — maneja automaticamente la enumeracion de shards, el checkpointing (rastrear cuales registros ya fueron procesados) y el balanceo de carga entre multiples instancias consumidoras.

Key PropertiesPropiedades Clave

Firehose is near real-time, not real-time — instead of forwarding each record immediately, it accumulates incoming data in an internal buffer and delivers it to the destination in batches. The buffer has two independent triggers running in parallel: it flushes when the accumulated data reaches a certain size, or when a time limit expires — whichever comes first. For example: configured at "5 MB or 60 seconds", a slow stream that never reaches 5 MB will still be delivered every 60 seconds. The minimum time interval is 60 seconds, which is why there's always at least a one-minute delay — that's what makes it "near" real-time and not real-time. Firehose es casi tiempo real, no tiempo real — en lugar de reenviar cada registro inmediatamente, acumula los datos entrantes en un buffer interno y los entrega al destino en lotes. El buffer tiene dos disparadores independientes que corren en paralelo: descarga cuando los datos acumulados alcanzan cierto tamano, o cuando expira un limite de tiempo — lo que ocurra primero. Por ejemplo: configurado a "5 MB o 60 segundos", un stream lento que nunca llega a 5 MB igual se entregara cada 60 segundos. El intervalo de tiempo minimo es 60 segundos, por eso siempre hay al menos un minuto de delay — eso es lo que lo hace "casi" tiempo real y no tiempo real.

There is no data storage and no replay: once data is delivered to the destination, it's gone from Firehose. Optionally, a Lambda function can transform records in-flight (e.g., CSV → JSON) before delivery. Built-in conversion to columnar formats (Parquet, ORC) and compression (GZIP, Snappy) are also supported. No hay almacenamiento de datos ni replay: una vez entregados al destino, desaparecen de Firehose. Opcionalmente, una funcion Lambda puede transformar registros en vuelo (ej. CSV → JSON) antes de la entrega. Tambien se soporta conversion nativa a formatos columnares (Parquet, ORC) y compresion (GZIP, Snappy).

• Long Polling: makes the consumer wait up to 20s for a message to arrive instead of returning immediately empty. Reduces API calls — has nothing to do with delaying delivery.
• Extended Client: for messages larger than 1 MiB. Stores the payload in S3 and sends a pointer. Completely unrelated to timing. Las cuatro opciones actuan en distintos momentos del ciclo de vida del mensaje — esa es la clave para distinguirlas:

• Visibility Timeout: oculta el mensaje despues de que un consumidor ya lo recibio (durante el procesamiento). Evita que otros consumidores lo agarren mientras se esta trabajando.
