# 23.17 - API Gateway Authentication and Authorization

**Section:** 23 - AWS Serverless: API Gateway

---

## The 3 Security Methods

### 1. IAM Authorization (+ Resource Policies)

- **Authentication:** IAM
- **Authorization:** IAM Policy
- **Best for:** Internal AWS users/roles (EC2, Lambda, IAM users within your account)
- **Technology:** Signature v4 (Sig v4) — credentials are signed and placed in request headers

```
Client → [Sig v4 headers] → API GW → checks with IAM → IAM policy check → Lambda
```

**Resource Policies** extend this for:
- **Cross-account access** — allow users/roles from other AWS accounts
- **IP address filtering** — whitelist or blacklist specific IPs
- **VPC Endpoint access** — allow only from a specific VPC

---

### 2. Cognito User Pools

- **Authentication:** Cognito (manages user lifecycle, token expiry)
- **Authorization:** Set at the API Gateway method level
- **Best for:** External users (web/mobile apps)
- **No custom code required** on the auth side

```
Client → authenticates with Cognito → receives token
       → passes token to API GW → API GW validates with Cognito
       → if valid → Lambda backend
```

> Authorization logic must still be implemented in the **backend Lambda function**.

---

### 3. Lambda Authorizer (formerly Custom Authorizer)

- **Authentication:** External / third-party (e.g. Auth0, OAuth, JWT)
- **Authorization:** Your Lambda function decides (returns an IAM policy)
- **Best for:** Third-party auth systems
- **Most flexible, most work**

```
Client → authenticates with 3rd party (e.g. Auth0) → receives token
       → passes token to API GW (header or query string)
       → API GW invokes Lambda Authorizer
       → Lambda verifies token with 3rd party
       → returns IAM policy → cached in Policy Cache
       → API GW allows/denies access to Lambda backend
```

- Result (IAM policy) is **cached** after first invocation
- You still **pay for each Lambda Authorizer invocation**

---

## Comparison Table

| | IAM | Cognito | Lambda Authorizer |
|---|---|---|---|
| **Auth** | IAM | Cognito | External/3rd party |
| **Authz** | IAM Policy | API GW method level | Lambda function |
| **Best for** | Internal AWS users | External users | 3rd party systems |
| **Custom code?** | No | No (auth side) | Yes |
| **Cross-account?** | Yes (+ resource policy) | No | No |
| **Technology** | Sig v4 | Cognito token | JWT / OAuth / bearer token |
| **Caching** | N/A | N/A | Policy result cached |

---

## Exam Tips

- **IAM + Sig v4** = internal AWS access (EC2, Lambda, IAM users)
- **Resource policy** = needed for cross-account access on top of IAM
- **Cognito** = external users, no custom auth code, but authz still in Lambda
- **Lambda Authorizer** = 3rd party auth, most flexible, returns IAM policy, result cached
- Lambda Authorizer = still pay per invocation even with caching
- Cognito = no custom implementation needed (preferred when managing your own users)
