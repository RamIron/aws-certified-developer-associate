# 23.2 - API Gateway Overview

**Section:** 23 - AWS Serverless: API Gateway

---

## Why API Gateway?

Three ways to expose a Lambda function to clients:

| Option | Requires | Notes |
|--------|----------|-------|
| Direct Lambda invocation | IAM permissions on client | Not practical for public clients |
| Application Load Balancer | Infrastructure to manage | Simple HTTP endpoint only |
| **API Gateway** | Nothing (serverless) | Full feature set ✅ |

---

## API Gateway Features

- **WebSocket Protocol** — real-time streaming
- **API Versioning** — v1 → v2 → v3 without breaking clients
- **Multiple environments** — dev / test / prod stages
- **Security** — authentication & authorization
- **API Keys & throttling** — protect from abuse
- **Swagger / Open API 3.0** — import & export API definitions
- **Request/response transformation & validation**
- **SDK & API spec generation**
- **Response caching**

---

## Integrations

### 1. Lambda Function (most common)
- Proxies requests to Lambda
- Full serverless stack: API GW → Lambda → DynamoDB

### 2. HTTP Endpoint
- Expose any HTTP backend (on-premises or cloud)
- Add API GW features (rate limiting, caching, auth, API keys) on top

### 3. AWS Service
- Expose any AWS service directly via API GW
- Example: Client → API GW → Kinesis Data Streams → Firehose → S3
- No AWS credentials needed by the client
- Add auth, rate control, public access on any AWS API

---

## Endpoint Types

| Type | Use Case | Notes |
|------|----------|-------|
| **Edge-Optimized** (default) | Global clients | Routes through CloudFront Edge locations; GW still in one region |
| **Regional** | Users in same region as GW | No CloudFront; can add your own CloudFront distribution |
| **Private** | VPC-only access | Uses interface VPC endpoints (ENIs); access controlled by resource policy |

---

## Security

| Method | Best For |
|--------|----------|
| **IAM Roles** | Internal apps (e.g., EC2 calling API GW) |
| **Amazon Cognito** | External users (mobile/web apps) |
| **Custom Authorizer** | Your own auth logic (Lambda function) |

### HTTPS / Custom Domain
- Integrate with **AWS Certificate Manager (ACM)**
- Edge-Optimized endpoint → certificate must be in **us-east-1**
- Regional endpoint → certificate must be in the **same region** as the API GW stage
- Set up a **CNAME or A-alias record in Route 53** to point your domain to API Gateway

---

## Exam Tips

- API Gateway = serverless REST API front door (no servers to manage)
- Default endpoint type = **Edge-Optimized**
- Private API GW = accessed only from within a **VPC**
- ACM cert for Edge-Optimized = **us-east-1** (this is a classic exam trick!)
- Three auth methods: IAM roles / Cognito / Custom Lambda authorizer
- API GW can proxy directly to AWS services (Kinesis, SQS, Step Functions, etc.)
