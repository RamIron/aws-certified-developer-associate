# 23.13 - API Gateway Caching

**Section:** 23 - AWS Serverless: API Gateway

---

## How Caching Works

```
Client → API GW → [cache hit?] → YES → return cached response
                               → NO  → call backend → cache result → return response
```

Reduces pressure on the backend by serving repeated requests from cache.

---

## Cache Settings

| Setting | Value |
|---------|-------|
| Default TTL | **300 seconds** (5 minutes) |
| Min TTL | 0 (disables caching) |
| Max TTL | **3600 seconds** (1 hour) |
| Cache size | **0.5 GB to 237 GB** |
| Encryption | Optional |
| Defined at | **Stage level** |
| Override | Per method (can disable cache for specific methods) |

> Cache is **expensive** — only makes sense in **production** (or pre-production). Not worth it for dev/test where traffic is low.

---

## Cache Invalidation

| Method | Who | Notes |
|--------|-----|-------|
| Flush entire cache | Admin via UI | Immediate |
| Per-request invalidation | Client | Send header: `Cache-Control: max-age=0` |

### Client Cache Invalidation — Security
- Clients need **IAM authorization** to invalidate the cache
- If no authorization is enforced → **any client can invalidate** → potential abuse
- If unauthorized request comes in, you can configure API GW to:
  - Ignore the `Cache-Control` header (safe default)
  - Fail with **403**
  - Add a warning

---

## Exam Tips

- Cache defined at **stage level**, can be overridden **per method**
- Default TTL = **300 seconds**, max = **3600 seconds**
- Cache size: **0.5 GB → 237 GB**
- Client invalidates with `Cache-Control: max-age=0` header
- Requires **IAM authorization** to invalidate — without it, anyone can flush the cache
- Cache is expensive → use in **production only**
