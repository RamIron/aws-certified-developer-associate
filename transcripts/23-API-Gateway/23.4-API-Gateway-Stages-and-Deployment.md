# 23.4 - API Gateway Stages and Deployment

**Section:** 23 - AWS Serverless: API Gateway

---

## Key Concepts

### 1. Stages & Deployments

- Changes to API Gateway are **not live until deployed** to a stage
- A stage = a named snapshot of your API (dev, test, prod, v1, v2...)
- Each stage gets its own URL: `https://{id}.execute-api.{region}.amazonaws.com/{stage}`
- Full deployment history is kept → **can roll back** to any previous deployment
- Multiple stages can coexist: v1 clients use `/v1`, v2 clients use `/v2`

```
api.example.com/v1  →  v1 stage  →  Lambda v1 function
api.example.com/v2  →  v2 stage  →  Lambda v2 function
```

### 2. Stage Variables

- Like environment variables, but for API Gateway stages
- Change configuration values **without redeploying the API**
- Can be used in: Lambda function ARN, HTTP endpoint, parameter mapping templates
- Passed to Lambda via the **context object**
- Format: `$stageVariables.variableName` (general reference)
- Inside a Lambda ARN string: `${stageVariables.variableName}` (curly braces required)

### 3. Stage Variables + Lambda Aliases Pattern

The most common exam pattern — decouple API GW stages from Lambda versions via aliases:

```
dev stage   → stageVar: lambdaAlias=dev   → dev alias   → Lambda $LATEST
test stage  → stageVar: lambdaAlias=test  → test alias  → Lambda v2
prod stage  → stageVar: lambdaAlias=prod  → prod alias  → 95% v1 / 5% v2
```

- API Gateway always calls the same ARN pattern: `function:$stageVariables.lambdaAlias`
- Traffic shifting (canary) is handled entirely at the Lambda alias level
- No need to update API Gateway when changing Lambda versions

---

## Exam Tips

- **Forgetting to deploy** = most common source of confusion (changes not live)
- Stage variables = env vars for API GW (passed to Lambda via context object)
- Stage variable format: `$stageVariables.myVar`
- Stage + Lambda alias pattern = decouple API GW from Lambda versioning
- Rollback = just redeploy a previous deployment from the stage history
