# 28.4 - Step Functions - Error Handling

## Overview

Error handling in Step Functions is one of its most powerful features. All error handling should happen **outside** the individual tasks, managed by the state machine itself — not inside the application code (e.g., Lambda functions).

---

## When Errors Occur

- **State machine definition issue** — e.g., no matching rule in a Choice state
- **Task failure** — e.g., Lambda function throws an exception
- **Transient failures** — e.g., network partition events

---

## Two Error Handling Mechanisms

### 1. Retry
Retries the failed task based on error type.

### 2. Catch
Transitions to a fallback state when retries are exhausted.

> **Key principle:** Define these in the state machine (JSON/ASL), NOT in the application code. This keeps Lambda functions small, fast, and simple.

---

## Predefined Error Codes

| Error Code           | Meaning                                                       |
|----------------------|---------------------------------------------------------------|
| `States.ALL`         | Matches any error name                                        |
| `States.Timeout`     | Task ran longer than `TimeoutSeconds` or no heartbeat received |
| `States.TaskFailed`  | Task execution failure (e.g., Lambda exception)               |
| `States.Permissions` | Insufficient permissions to execute                           |

States can also report their own custom errors.

---

## Retry Configuration

Evaluated **top to bottom**. Fields:

| Field           | Description                                                  |
|-----------------|--------------------------------------------------------------|
| `ErrorEquals`   | List of error codes this retry block applies to              |
| `IntervalSeconds` | Seconds to wait before the first retry                     |
| `BackoffRate`   | Multiplier applied to the interval after each retry (exponential backoff) |
| `MaxAttempts`   | Max number of retries (default: 3; 0 = never retry)          |

### Example ASL Retry block:
```json
"Retry": [
  {
    "ErrorEquals": ["CustomError"],
    "IntervalSeconds": 1,
    "BackoffRate": 2,
    "MaxAttempts": 2
  },
  {
    "ErrorEquals": ["States.TaskFailed"],
    "IntervalSeconds": 30,
    "BackoffRate": 2,
    "MaxAttempts": 2
  },
  {
    "ErrorEquals": ["States.ALL"],
    "IntervalSeconds": 5,
    "BackoffRate": 2,
    "MaxAttempts": 5
  }
]
```

Once all retries are exhausted → **Catch block kicks in**.

---

## Catch Configuration

Evaluated **top to bottom**. Fields:

| Field         | Description                                                     |
|---------------|-----------------------------------------------------------------|
| `ErrorEquals` | List of error codes this catch block applies to                 |
| `Next`        | Name of the state to transition to on match                     |
| `ResultPath`  | Where to put the error info in the state's output (e.g., `$.error`) |

### Example ASL Catch block:
```json
"Catch": [
  {
    "ErrorEquals": ["CustomError"],
    "Next": "CustomErrorFallback",
    "ResultPath": "$.error"
  },
  {
    "ErrorEquals": ["States.ALL"],
    "Next": "CatchAllFallback",
    "ResultPath": "$.error"
  }
]
```

---

## ResultPath — Key Exam Topic

`ResultPath` determines what input is sent to the next state after a catch.

- **Without ResultPath** — the error replaces the entire input
- **With `ResultPath: "$.error"`** — the original input is preserved AND the error is appended under the `$.error` key

### Example:

**Input to failed task:**
```json
{ "foo": "bar" }
```

**Output sent to next state (with `ResultPath: "$.error"`):**
```json
{
  "foo": "bar",
  "error": {
    "Error": "CustomError",
    "Cause": "Something went wrong"
  }
}
```

This allows downstream states to log, alert, or debug using both the original input and the error details.

---

## Benefits of Step Functions Error Handling

- Lambda functions stay **small and fast** (no retry loops inside them)
- Error handling logic can be changed **without redeploying** Lambda
- Full **execution history** of retries and catches is visible in the Step Functions console
- Centralized, declarative error handling in JSON/ASL

---

## Exam Tips

- ✅ Retry and Catch are evaluated **top to bottom**
- ✅ `MaxAttempts: 0` means never retry
- ✅ `States.ALL` catches any error
- ✅ `ResultPath: "$.error"` preserves original input + appends error info
- ✅ After all retries exhausted → Catch block activates
- ✅ Error handling belongs in the **state machine**, not in the Lambda function
