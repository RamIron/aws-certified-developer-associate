### State machine: MyStateMachineError
- Authored from scratch using a pre-written JSON definition (`1-error-handling/state-machine.json`)
- Three fallback paths: `CustomErrorFallback`, `ReservedTypeFallback`, `CatchAllFallback`

---

## Key observations from execution

### Run 1 — Lambda throws `CustomError`
- Step Functions matched the first Retry block (`ErrorEquals: ["CustomError"]`)
- Retry sequence: fail → wait 1s → fail → wait 2s → fail (MaxAttempts: 2 = 2 retries)
- After retries exhausted → Catch matched `CustomError` → transitioned to `CustomErrorFallback`
- **Execution: succeeded** (via fallback path)

### Run 2 — Lambda throws `NotCustomError` (unmatched error)
- First Retry block (`CustomError`) didn't match
- Second Retry block (`States.TaskFailed`) matched
- Retry sequence: fail → wait 30s → fail → wait 60s → fail (BackoffRate 2 doubled the interval)
- After retries exhausted → Catch matched `States.TaskFailed` → transitioned to `ReservedTypeFallback`
- **Execution: succeeded** (via different fallback path)

---

## Key takeaways

- **Different errors → different retry timing**: CustomError retried every ~1s; TaskFailed retried every 30–60s
- **Different errors → different catch branches**: routing is fully controlled by the error type
- **BackoffRate doubles the interval**: 30s → 60s is clearly visible in the event history elapsed time
- **Event history** shows every attempt: Lambda started → failed → scheduled (retry) → started → failed...
- State machines can be left running without cost (Standard workflow charges per state transition)
