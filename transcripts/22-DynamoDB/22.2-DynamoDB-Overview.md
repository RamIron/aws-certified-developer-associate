# 22.2 - DynamoDB Overview

**Section:** 22 - AWS Serverless: DynamoDB

---

## Key Concepts

### 1. SQL vs NoSQL — The Fundamental Difference

**RDBMS (SQL):**
- Strong schema, tables, joins, aggregations
- Scales mostly **vertically** (bigger CPU/RAM)
- Horizontal scaling limited to read replicas (no horizontal write scaling)

**NoSQL:**
- Non-relational, distributed
- No query joins (or very limited)
- No aggregations (SUM, AVG, etc.)
- All data needed must be in **one row**
- Scales **horizontally** (reads AND writes)

---

### 2. DynamoDB Feature Overview

- Fully managed NoSQL, highly available
- Replication across **multiple AZs** out of the box
- Scales to: millions of req/sec, trillions of rows, hundreds of TB
- Fast and consistent performance — **single-digit millisecond latency**
- Integrated with IAM (security, authorization, administration)
- **DynamoDB Streams** → event-driven programming
- Low cost + auto scaling
- Two table classes: **Standard** and **Infrequent Access (IA)**

---

### 3. Table Structure

| Concept | Description |
|---|---|
| Table | Top-level entity |
| Item (row) | One record in the table. Max **400 KB** |
| Attribute | A field in an item. Can be null, nested, added over time |
| Schema | Flexible — no need to define all attributes upfront |

**Data types:**
- Scalar: String, Number, Binary, Boolean, Null
- Document: List, Map (nesting)
- Set: String Set, Number Set, Binary Set

---

### 4. Primary Key — Option 1: Partition Key only

Also called: **Hash strategy**

- Partition key must be **unique** per item
- Must have **high cardinality** (diverse values) for good data distribution

Example — Users table:

| User_ID (PK) | First_Name | Last_Name | Age |
|---|---|---|---|
| u1 | John | Doe | 30 |
| u2 | Jane | (null) | 25 |
| u3 | Bob | Smith | 40 |

---

### 5. Primary Key — Option 2: Partition Key + Sort Key

Also called: **Hash + Range**

- **Combination** of both must be unique per item
- Data is **grouped by partition key**, ordered by sort key
- Allows same partition key with different sort keys

Example — Users-Games table:

| User_ID (PK) | Game_ID (SK) | Score | Result |
|---|---|---|---|
| u1 | game_1 | 92 | win |
| u2 | game_2 | 14 | lose |
| u2 | game_3 | 55 | win |  ← same PK, different SK ✅

---

### 6. Choosing a Good Partition Key

**Rule: choose the attribute with the highest cardinality.**

Example — Movie database. Best partition key?
- `movie_id` ✅ — unique per movie, maximum distribution
- `producer_name` ❌ — few values, data clusters around popular producers
- `lead_actor_name` ❌ — skewed towards popular actors
- `movie_language` ❌ — very few values (mostly "English"), heavy skew

> **Exam tip:** Always choose the partition key with the **most distinct values** to ensure even data distribution across DynamoDB partitions.

## PutItem Overwrite Behavior (from AWS docs)

Writing an item with the same primary key as an existing item **completely replaces** it — no error is thrown. This is the default behavior of `PutItem`. It's a full replacement: any attributes in the old item that aren't in the new one are **deleted**.

- To detect if an overwrite happened: use `ReturnValues = ALL_OLD`
- To **prevent** overwriting: use a condition expression with `attribute_not_exists(pk)`

This behavior will be covered in practice in lesson 22.8 - Conditional Writes.

---

## Exam Tips

- DynamoDB is **NoSQL**, not relational — no joins, no aggregations
- Multi-AZ replication is **built-in**, no configuration needed
- Max item size: **400 KB**
- Must define primary key **at table creation time** (cannot change later)
- Best partition key = **highest cardinality**
