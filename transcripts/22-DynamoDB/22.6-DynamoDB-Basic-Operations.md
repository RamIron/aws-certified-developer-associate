# 22.6 - DynamoDB Basic Operations

## Key Concepts

### 1. Write APIs

| API | Behavior | Use Case |
|---|---|---|
| **PutItem** | Creates new item OR **fully replaces** existing item with same PK | Full write / overwrite |
| **UpdateItem** | Edits specific attributes of an existing item, or creates item if it doesn't exist | Partial update |
| **Conditional Writes** | Accept write/update/delete only if a condition is met | Concurrent access control |

- PutItem → full replacement (all old attributes not in new item are lost)
- UpdateItem → surgical edit (only touched attributes change)
- Conditional Writes → covered in depth in lesson 22.8

---

### 2. Read APIs

#### GetItem
- Read a single item by its **exact Primary Key** (HASH or HASH+RANGE)
- Supports Eventually Consistent (default) or Strongly Consistent reads
- Can use **ProjectionExpression** → return only specific attributes (saves RCU + bandwidth)

#### Query
- Returns items for a **specific Partition Key** (must use `=` operator)
- Optional: filter by Sort Key (`=`, `<`, `>`, `between`, `begins_with`, etc.)
- **FilterExpression**: additional filtering *after* the query, *before* returning data
  - Applied server-side but **after** key-based reads — does NOT save RCU
  - Can only filter on **non-key attributes**
- Returns up to **1 MB** of data or the `Limit` count — use **pagination** for more
- Can query a table, LSI, or GSI

#### Scan
- Reads the **entire table** — very inefficient
- Returns up to **1 MB** per call → use pagination for full export
- Consumes a lot of RCU (reads every item)
- Use `Limit` to reduce impact on live traffic
- **Parallel Scan**: multiple workers scan multiple segments simultaneously → faster but consumes more RCU
- Can use ProjectionExpression and FilterExpression

**Query vs Scan:**
| | Query | Scan |
|---|---|---|
| Reads | Only items with matching PK | Entire table |
| Efficiency | Efficient | Very inefficient |
| Use case | Normal app queries | Data export / analytics |

---

### 3. Delete APIs

| API | Behavior |
|---|---|
| **DeleteItem** | Deletes a single item. Supports conditional delete. |
| **DeleteTable** | Drops the entire table + all items instantly |

> **Exam tip:** To delete all data from a table, use `DeleteTable` — NOT a Scan + delete loop. Much faster and cheaper.

---

### 4. Batch Operations

Batch = multiple operations in a single API call → fewer round trips, lower latency.
All operations in a batch run **in parallel** by DynamoDB.
Part of a batch can fail → failed items returned as **UnprocessedItems** / **UnprocessedKeys**.
Retry strategy: exponential backoff, or add more RCU/WCU if it keeps failing.

| API | Operations | Limits |
|---|---|---|
| **BatchWriteItem** | Up to 25 PutItem + DeleteItem (no UpdateItem) | 16 MB total, 400 KB per item |
| **BatchGetItem** | Reads from one or more tables | Up to 100 items, 16 MB total |

---

### 5. PartiQL

- SQL interface for DynamoDB — same API capabilities, just written as SQL
- Supports: `SELECT`, `INSERT`, `UPDATE`, `DELETE`
- **No JOINs** (DynamoDB is NoSQL — joins don't exist)
- Can query across multiple tables
- Runs from: Management Console, NoSQL Workbench, DynamoDB APIs, CLI, SDK
- Goal: let SQL-fluent developers use DynamoDB without learning new API syntax

---

## Exam Tips
- **PutItem** = full replace; **UpdateItem** = partial update
- **FilterExpression** does NOT reduce RCU consumed — filtering happens after reads
- **FilterExpression** cannot be used on key attributes (PK or SK)
- **Scan** is inefficient — use Query when possible
- To delete all table data → use `DeleteTable`, not Scan + delete
- **BatchWriteItem** does NOT support UpdateItem
- UnprocessedItems / UnprocessedKeys → retry with exponential backoff or add capacity
- PartiQL = SQL syntax for DynamoDB, but no JOINs
