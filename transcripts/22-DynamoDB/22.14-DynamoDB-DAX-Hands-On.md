# 22.14 - DynamoDB DAX - Hands On

> Hands-on walkthrough of DAX cluster creation. Core concepts covered in 22.13.

## New Info

### DAX is NOT in the free tier
- Creating a DAX cluster will incur costs

### Node Types
- **t-type** (e.g. t2.small): burstable, for lower throughput / dev environments
- **r-type** (e.g. r5.large): memory-optimized, for always-ready production capacity
- Node type cannot be changed after creation — must create a new cluster to change it

### Cluster Size
- Up to **11 nodes** (lesson 22.13 said 10 — 11 is the actual console limit)
- 1 node = single AZ, development use, reduced availability
- 3 nodes = recommended minimum for Multi-AZ / production HA

### Networking
- DAX lives inside a **VPC + subnet group** — just like RDS
- Requires a **security group** with port **8111** open (or **9111** for in-transit encryption)

### IAM Role
- DAX cluster needs an **IAM Service Role** to access DynamoDB on your behalf
- Role grants read/write access — can be scoped to specific tables

### TTL Configuration (Parameter Groups)
- Item cache TTL: **5 minutes** (default)
- Query cache TTL: **5 minutes** (default)
- Configurable via **Parameter Groups** (same concept as RDS parameter groups)

### Cluster Endpoint
- After creation, DAX provides a **cluster endpoint**
- Your application points to this endpoint instead of the DynamoDB endpoint
- No code changes needed beyond swapping the endpoint — seamless integration

### Monitoring
- CloudWatch metrics available: **cache hits**, **cache misses**, CPU utilization
- Useful to validate if DAX is actually being effective for your workload
