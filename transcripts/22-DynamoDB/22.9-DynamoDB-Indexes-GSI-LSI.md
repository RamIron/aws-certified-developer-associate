# 22.9 - DynamoDB Indexes (GSI + LSI)

## Key Concepts

### 1. LSI — Local Secondary Index

- Provides an **alternative sort key** for your table
- **Same partition key** as the base table — only the sort key changes
- Sort key must be a scalar: String, Number, or Binary
- Up to **5 LSIs per table**
- **Must be defined at table creation time** — cannot add later
- Uses the **same RCU/WCU** as the main table — no separate capacity needed
- You can project all or some attributes from the main table onto the LSI

**Use case:** you want to query by the same partition key but sort/filter by a different attribute.

**Example:**
```
Base table:  PK = user_id  |  SK = game_id
LSI:         PK = user_id  |  SK = game_timestamp  ← new sort key

Now you can query: "give me all games for user X between date A and date B"
Without LSI → you'd have to Scan + filter client-side (inefficient)
```

---

### 2. GSI — Global Secondary Index

- Provides a completely **alternative primary key** — different partition key (and optional sort key)
- Like creating a **new table** with a different access pattern
- Must provision **separate RCU/WCU** for the GSI
- Attributes projected onto the GSI are your choice
- Can be **added or modified after table creation** — more flexible than LSI

**Use case:** you want to query by an attribute that is not the partition key of the main table.

**Example:**
```
Base table:  PK = user_id  |  SK = game_id  |  attrs: game_timestamp
GSI:         PK = game_id  |  SK = game_timestamp  |  projected: user_id

Now you can query: "who played game X and when?"
Without GSI → impossible without a full Scan
```

---

### 3. LSI vs GSI Comparison

| | LSI | GSI |
|---|---|---|
| Partition key | Same as base table | Different from base table |
| Sort key | Different from base table | Optional, different |
| Created | At table creation time ONLY | Anytime (add/modify after creation) |
| Capacity | Shares main table RCU/WCU | Requires own provisioned RCU/WCU |
| Throttling | No special consideration | GSI throttling → main table throttles too ⚠️ |

---

### 4. GSI Throttling — Exam Critical ⚠️

- If writes are throttled on a **GSI**, the **main table will also be throttled**
- This happens even if the main table has plenty of WCU capacity left
- Root cause: GSI needs its own write capacity to replicate data
- Solution: choose GSI partition key carefully (high cardinality) and provision enough WCU on the GSI

```
Main table WCU: 100 (plenty of capacity)
GSI WCU: 5 (too low → throttled)
Result: BOTH GSI and main table are throttled ❌
```

LSI does NOT have this problem — it shares capacity with the main table.

---

## Exam Tips
- LSI = same PK, different SK → must define at creation time
- GSI = different PK (and optional SK) → can add after creation
- GSI has its own RCU/WCU → GSI throttle = main table throttle ⚠️
- LSI shares main table capacity → no extra throttling concern
- Both LSI and GSI support attribute projection (all, some, or keys only)
- Up to 5 LSIs per table
- Need to query on a non-key attribute? → GSI
- Need to sort by a different attribute within same partition? → LSI
