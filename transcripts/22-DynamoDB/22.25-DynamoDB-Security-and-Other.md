# 22.25 - DynamoDB Security & Other

## Key Concepts

### 1. Security Features

| Feature | Details |
|---|---|
| **VPC Endpoints** | Access DynamoDB privately, without going through the public internet |
| **IAM** | Full access control — who can do what on which tables |
| **Encryption at rest** | AWS KMS (managed or customer-managed keys) |
| **Encryption in transit** | SSL / TLS |

---

### 2. Backup & Restore

| Type | Details |
|---|---|
| **Point-in-Time Recovery (PITR)** | Restore to any point in time, no performance impact |
| **On-demand backup** | Manual backup, restore when needed |

Same PITR concept as RDS.

---

### 3. Global Tables

- **Multi-region, multi-active, fully replicated** DynamoDB table
- Reads and writes accepted in ANY region — not just one primary region
- High performance, low latency for global users
- **Requirement: DynamoDB Streams must be enabled** (replication uses Streams under the hood)

---

### 4. DynamoDB Local

- A **local simulation** of DynamoDB running on your computer
- Used for **development and testing** without hitting the real AWS service
- No cost, no network needed
- Useful for CI/CD pipelines and local integration tests

---

### 5. AWS DMS (Database Migration Service)

- Used to migrate data **to and from** DynamoDB
- Supports: MongoDB → DynamoDB, DynamoDB → Oracle/MySQL/S3, and more

---

### 6. Fine-Grained Access Control ⚠️

**Problem:** Mobile/web clients need to access DynamoDB directly, but you can't give each user an IAM user — security hole and unmanageable at scale.

**Solution:** Federated identity + temporary credentials + IAM condition on LeadingKeys.

```
Flow:
  User → logs in with identity provider
           (Cognito, Google, Facebook, SAML, OpenID Connect)
       → receives temporary AWS credentials
       → assumes an IAM role
       → IAM role has conditions that restrict access

IAM Condition — LeadingKeys (row-level security):
  Only allow access to items where PK = the user's own identity
  → user can only read/write their OWN data

IAM Condition — Attributes (column-level security):
  Only allow access to specific attributes of an item
  → user sees only the fields they're allowed to see
```

**Sample policy condition:**
```json
"Condition": {
  "ForAllValues:StringEquals": {
    "dynamodb:LeadingKeys": ["${cognito-identity.amazonaws.com:sub}"]
  }
}
```
The `${cognito-identity.amazonaws.com:sub}` is replaced at runtime with the actual user's identity.

---

## Exam Tips
- Global Tables = multi-region multi-active → **requires DynamoDB Streams**
- DynamoDB Local = local dev/test, no AWS needed
- Fine-grained access: federated login → temp credentials → IAM role with conditions
- **LeadingKeys** = row-level security (restrict by PK)
- **Attributes condition** = column-level security (restrict by attribute)
- DMS = migration tool (MongoDB → DynamoDB etc.)
