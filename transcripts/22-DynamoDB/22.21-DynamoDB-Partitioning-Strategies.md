# 22.21 - DynamoDB Partitioning Strategies

## Key Concept — Write Sharding

**Problem:** Low-cardinality partition keys create hot partitions.

Example: voting app with only `candidate_a` and `candidate_b` as partition keys
→ All writes go to just 2 partitions → hot partition issue 🔥

**Solution: Write Sharding** — add a random or calculated suffix/prefix to the partition key to distribute writes across more partitions.

```
Without sharding:
  candidate_a → Partition 1  (all A votes)
  candidate_b → Partition 2  (all B votes)
  → Hot partitions ❌

With sharding (random suffix):
  candidate_a_11 → Partition 3
  candidate_a_20 → Partition 7
  candidate_b_17 → Partition 1
  candidate_b_18 → Partition 5
  → Distributed writes ✅
```

**Two suffix strategies:**
| Strategy | How | Use case |
|---|---|---|
| Random suffix | Append random number (e.g. 1–20) | Maximum distribution |
| Calculated suffix | Hash-based suffix | Deterministic, reproducible distribution |

**Trade-off:** reads become harder — you now need to query all shards and aggregate results in your app (e.g. sum all `candidate_a_*` votes).

---

## Exam Tips
- Write sharding = solution for hot partition due to low-cardinality partition key
- Add random or hash-based suffix/prefix to partition key value
- Increases write distribution at the cost of more complex reads
