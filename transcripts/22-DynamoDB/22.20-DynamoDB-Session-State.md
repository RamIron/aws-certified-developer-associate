# 22.20 - DynamoDB Session State

## Key Concept — Session State Storage Comparison

Web apps need to store session state (e.g. user login) and share it across multiple backend instances.

| Service | Type | Shared? | Best for |
|---|---|---|---|
| **DynamoDB** | Serverless key/value DB | ✅ Yes | Auto-scaling, serverless session store |
| **ElastiCache** | In-memory key/value cache | ✅ Yes | Ultra-fast, fully in-memory session store |
| **EFS** | Network file system | ✅ Yes (via network drive) | File-based session sharing across EC2 |
| **EBS** | Block storage | ❌ No (one EC2 only) | Local caching only — NOT shared |
| **EC2 Instance Store** | Local disk | ❌ No (one EC2 only) | Local caching only — NOT shared |
| **S3** | Object storage | ✅ Yes | ❌ High latency, meant for large files — not ideal |

---

### DynamoDB vs ElastiCache for Session State

Both are key/value stores that can store session data. Choose based on:

```
ElastiCache → "in memory", ultra-low latency, fastest option
DynamoDB    → "serverless", automatic scaling, durable
```

| | DynamoDB | ElastiCache |
|---|---|---|
| Storage | Persistent (disk-backed) | In-memory only |
| Scaling | Automatic (serverless) | Manual cluster sizing |
| Latency | Single-digit ms | Sub-millisecond |
| Keyword on exam | "serverless", "auto-scaling" | "in-memory", "fastest" |

---

## Exam Tips
- Session state = DynamoDB or ElastiCache (best options)
- "In-memory session store" → **ElastiCache**
- "Serverless / auto-scaling session store" → **DynamoDB**
- EFS = shared file system, works but is file-based not DB
- EBS / Instance Store = local only, cannot share across instances ❌
- S3 = high latency, not suitable for session state ❌
