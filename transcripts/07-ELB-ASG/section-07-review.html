Connection Draining / Deregistration DelayDrenado de conexiones / Retraso de cancelación de registro

When an instance is taken out of service — due to a deployment, scale-in event, or a failed health check — there may be requests already in progress on that instance. Without draining, those connections would be cut immediately, causing errors for users mid-request. Connection Draining tells the ELB: "stop sending new traffic to this instance, but give it time to finish what it's already handling." Cuando una instancia se retira del servicio — por un despliegue, un evento de reducción de escala o un health check fallido — puede haber solicitudes ya en curso en esa instancia. Sin drenado, esas conexiones se cortarían inmediatamente, causando errores a los usuarios. Connection Draining le dice al ELB: "deja de enviar tráfico nuevo a esta instancia, pero dale tiempo para terminar lo que ya está procesando."

How it worksCómo funciona

The diagram below shows what happens when an instance enters draining state. New requests go to healthy instances; existing in-flight requests are allowed to finish.El diagrama muestra qué ocurre cuando una instancia entra en estado de drenado. Las nuevas solicitudes van a instancias saludables; las solicitudes en curso pueden terminar.

💧

Two names, same featureDos nombres, misma función

Connection Draining is the name used with Classic Load Balancers. Deregistration Delay is the name used with ALB, NLB, and GWLB (target groups). They work identically. Connection Draining es el nombre usado con Classic Load Balancers. Deregistration Delay es el nombre usado con ALB, NLB y GWLB (grupos objetivo). Funcionan igual.

⏳

What the timer controlsQué controla el temporizador

The timer is a maximum wait. ELB waits up to this long for in-flight requests to complete. If all requests finish sooner, the instance deregisters immediately — no need to wait out the full timer. El temporizador es una espera máxima. ELB espera como máximo este tiempo para que las solicitudes en curso finalicen. Si terminan antes, la instancia se cancela inmediatamente — no hace falta esperar todo el tiempo.

Choosing the right timeout valueElegir el valor de timeout correcto

The default is 300 s (5 min). The right value depends on how long your typical requests take.El valor predeterminado es 300 s (5 min). El valor correcto depende de cuánto tardan tus solicitudes típicas.

Warm-up time does NOT auto-extend. If a new instance fails health checks during a refresh, the refresh PAUSES (because it cannot maintain the minimum healthy percentage). It does NOT extend the warm-up timer. The timer is fixed — once it expires, that instance is considered done regardless of health.El tiempo de calentamiento NO se extiende automáticamente. Tricky Quiz Questions Preguntas Tricky del Quiz

Q: An organization wants to analyze incoming ALB requests to study latencies and client IP patterns. Which feature helps collect this data? P: Una organización quiere analizar las solicitudes entrantes del ALB para estudiar latencias y patrones de IPs de clientes. ¿Qué característica ayuda a recopilar esta información?

✅ Answer: ALB Access Logs (stored in S3)✅ Respuesta: Logs de acceso del ALB (almacenados en S3)

Why not the others? CloudWatch Metrics gives aggregates (counts, average latency) — not per-request detail. CloudTrail logs API calls to AWS (e.g. CreateLoadBalancer) — not HTTP traffic. ALB Request Tracing adds an X-Amzn-Trace-Id header to individual requests for tracing through backends, but does not store or aggregate data for analysis. Access Logs capture every request (timestamp, client IP, latencies, request path, response code) and store them in S3 — the only option for per-request analysis at scale. ¿Por qué no las otras? CloudWatch Metrics da agregados (conteos, latencia promedio) — no detalle por solicitud. CloudTrail registra llamadas a la API de AWS (ej. CreateLoadBalancer) — no el tráfico HTTP. El rastreo de solicitudes del ALB agrega un header X-Amzn-Trace-Id para rastrear a través de backends, pero no almacena ni agrega datos para análisis. Los Logs de acceso capturan cada solicitud (timestamp, IP del cliente, latencias, ruta, código de respuesta) y los guardan en S3 — la única opción para análisis por solicitud a escala.
