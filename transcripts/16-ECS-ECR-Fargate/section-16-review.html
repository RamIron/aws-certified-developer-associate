★ — ECS Building Blocks: How the Layers Nest★ — Bloques de ECS: cómo se anidan las capas
Cluster, Instance, Task, Container — who contains who?Cluster, Instancia, Task, Container — ¿quién contiene a quién?

ECS throws a lot of similar-sounding names at you — cluster, service, task, task definition, agent, container, instance. The trick to stop feeling lost is to split them into two groups: the layers that physically nest inside one another (and run + consume CPU/RAM), and the cross-cutting pieces that manage or describe them but aren't a nesting layer.ECS te tira un montón de nombres parecidos — cluster, service, task, task definition, agent, container, instancia. El truco para dejar de marearte es separarlos en dos grupos: las capas que se anidan físicamente una dentro de otra (y corren + consumen CPU/RAM), y las piezas transversales que las administran o describen pero no son una capa anidada.

"A task runs one or more containers" vs "an instance has many tasks" — both are true. There's no contradiction: there are three nesting levels, not two. A task contains containers, but is itself contained by an instance: instance ⊃ task ⊃ container."Una task corre uno o más containers" vs "una instancia tiene muchas tasks" — las dos son ciertas. No hay contradicción: hay tres niveles de anidado, no dos. Una task contiene containers, pero a su vez está contenida por una instancia: instancia ⊃ task ⊃ container.

The nesting, visualizedEl anidado, visualizado

Read it like Russian dolls, outside-in: a cluster holds EC2 instances; each instance (with its ECS Agent) holds several tasks; each task holds one or more containers. The Service and Task Definition on the right are cross-cutting — they act on the tasks but are not nesting layers.Leelo como muñecas rusas, de afuera hacia adentro: un cluster contiene instancias EC2; cada instancia (con su ECS Agent) contiene varias tasks; cada task contiene uno o más containers. El Service y el Task Definition de la derecha son transversales — actúan sobre las tasks pero no son capas anidadas.

Fargate caveat: with Fargate the instance + Agent layer disappears — AWS runs the tasks for you, so there's nothing to "fill" or manage. The chain shrinks to Cluster ⊃ Task ⊃ Container. (This is also why task placement strategies only apply to the EC2 launch type.)Detalle de Fargate: con Fargate desaparece la capa de instancia + Agent — AWS corre las tasks por vos, así que no hay nada que "llenar" ni administrar. La cadena se reduce a Cluster ⊃ Task ⊃ Container. (Por eso también las task placement strategies solo aplican al launch type EC2.)

Scaling PoliciesPolíticas de escalado
Target TrackingSeguimiento de objetivo

You set a target value for a metric — AWS figures out how many tasks to add or remove to stay near that target. You don't define the step sizes; the algorithm does it automatically.Definís un valor objetivo para una métrica — AWS calcula cuántas tareas agregar o quitar para mantenerse cerca de ese objetivo. No definís los tamaños de paso; el algoritmo lo hace automáticamente.

Example: Target CPU = 60%. At 80% CPU → AWS adds tasks automatically. At 40% CPU → AWS removes tasks. You never say "add 2" or "add 5" — AWS decides the amount.Ejemplo: Objetivo CPU = 60%. Si CPU llega al 80% → AWS agrega tareas solo. Si baja al 40% → AWS las quita. Nunca decís "agregar 2" o "agregar 5" — AWS decide la cantidad.

Step ScalingEscalado por pasos

Scale by specific amounts based on CloudWatch Alarm thresholds. Unlike Target Tracking (which reacts continuously), Step Scaling fires when an alarm crosses a defined boundary — and you decide exactly how many tasks to add or remove per step.Escala en cantidades específicas según umbrales de alarmas de CloudWatch. A diferencia del seguimiento de objetivo (que reacciona continuamente), Step Scaling se dispara cuando una alarma cruza un umbral definido — y vos decidís exactamente cuántas tareas agregar o quitar por paso.

Example: CPU > 70% → add 2 tasks  ·  CPU > 90% → add 5 tasks  ·  CPU < 30% → remove 1 task. Each threshold = one step.Ejemplo: CPU > 70% → agregar 2 tareas  ·  CPU > 90% → agregar 5 tareas  ·  CPU < 30% → quitar 1 tarea. Cada umbral = un paso.

Scheduled ScalingEscalado programado

Pre-scale for known traffic patterns (e.g., every Monday morning). Anticipate demand before it arrives.Pre-escalar para patrones de tráfico conocidos (ej: cada lunes a la mañana). Anticipar la demanda antes de que llegue.

EC2 Launch Type — Cluster Capacity Provider: Auto Scaling on ECS tasks is not enough — you also need more EC2 instances. Use an ECS Cluster Capacity Provider (backed by an ASG) to automatically provision EC2 capacity when tasks can't be placed. A plain ASG alone is not sufficient.Tipo de lanzamiento EC2 — Cluster Capacity Provider: El Auto Scaling en tareas ECS no es suficiente — también se necesitan más instancias EC2. Usar un ECS Cluster Capacity Provider (respaldado por un ASG) para provisionar capacidad EC2 automáticamente cuando las tareas no se pueden colocar. Un ASG solo no es suficiente.
