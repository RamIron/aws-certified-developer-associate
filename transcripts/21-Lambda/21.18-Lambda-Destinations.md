# 21.18 - Lambda Destinations

> Udemy Lecture #281 · Section 21: AWS Serverless: Lambda

## Key Concepts

### 1. The Problem Destinations Solve

With async invocations and event source mappings, it was hard to know if processing succeeded or failed, and to retrieve that data. Destinations fix this.

### 2. Destinations for Asynchronous Invocations

You can configure TWO destinations — one for success, one for failure:

```
                          ┌──────────────────────────┐
                          │ Success Destination       │
                     ✅ → │ (SQS, SNS, Lambda,       │
                          │  EventBridge)             │
S3 event → Lambda ───┤    └──────────────────────────┘
                     │    ┌──────────────────────────┐
                     ❌ → │ Failure Destination       │
                          │ (SQS, SNS, Lambda,       │
                          │  EventBridge)             │
                          └──────────────────────────┘
```

4 possible targets: **SQS, SNS, Lambda, EventBridge**

### 3. Destinations vs DLQ

| | DLQ (old) | Destinations (new, recommended) |
|---|---|---|
| **Success events** | No | ✅ Yes |
| **Failure events** | Yes | ✅ Yes |
| **Targets** | SQS, SNS only | SQS, SNS, Lambda, EventBridge |
| **Recommendation** | Still works | **Use this instead** |

Both can be used at the same time, but **Destinations are recommended** because they're newer and support more targets + success events.

### 4. Destinations for Event Source Mapping

Only for **discarded event batches** (failures only, no success destination):

```
Kinesis / DDB Stream
       ↓
  Event Source Mapping → Lambda → keeps failing
                                       ↓
                              Discarded event batch
                                       ↓
                              ┌──────────────────┐
                              │ Failed Destination │
                              │ (SQS or SNS)      │
                              └──────────────────┘
```

This prevents the shard from being blocked forever — instead of retrying endlessly, discard the batch and send it to a destination.

**Key difference from async destinations:** Event Source Mapping destinations are **failure only** (discarded batches). No success destination available. And targets are limited to **SQS or SNS** (no Lambda or EventBridge).

### Summary: Destinations by Invocation Type

```
ASYNC INVOCATION:
  Lambda succeeds → Success Destination (SQS/SNS/Lambda/EventBridge)
  Lambda fails    → Failure Destination (SQS/SNS/Lambda/EventBridge)

EVENT SOURCE MAPPING:
  Batch discarded → Failed Destination (SQS or SNS only)
  Batch succeeds  → (no success destination available)
```

### 5. SQS Special Case

If Event Source Mapping reads from **SQS**, you have two options for handling failures:
- Set a **Destination** on the Event Source Mapping (failed events → SQS/SNS)
- Set a **DLQ** directly on the SQS queue itself

Either works — pick one.

---

## Exam Tips

- Destinations = **modern replacement for DLQ** (recommended by AWS)
- Async: destinations support **both success AND failure** → SQS, SNS, Lambda, EventBridge
- DLQ: only supports **failure** → SQS, SNS only
- Event Source Mapping destinations: **failure only** (discarded batches) → SQS, SNS
- "Where to send successful async results?" → **Destination** (DLQ can't do this)
- SQS as source: choose between DLQ on queue OR failed destination — both work
