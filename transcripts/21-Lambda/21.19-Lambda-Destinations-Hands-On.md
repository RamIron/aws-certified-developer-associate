# 21.19 - Lambda Destinations Hands On

> Udemy Lecture #282 · Section 21: AWS Serverless: Lambda

## Hands-On Summary

### Setup
1. Create two SQS queues: `s3-success` and `s3-failure`
2. Go to Lambda function (`lambda-s3`) → Configuration → **Destinations**
3. Add destination: Async invocation → **On failure** → SQS → `s3-failure`
4. Add destination: Async invocation → **On success** → SQS → `s3-success`

### Permissions (auto-added)
- Lambda console detects missing permissions and **auto-adds** them when you save
- Adds `AmazonLambdaSQSQueueDestinationExecutionRole` to the IAM execution role
- Allows `sqs:SendMessage` to the specific destination queue

### Testing Success
1. Upload `beach.jpeg` to S3 bucket → triggers Lambda asynchronously
2. Lambda processes successfully → returns status 200
3. SQS `s3-success` → **1 message available**

**Success message body contains:**
```json
{
  "requestContext": {
    "condition": "Success",
    "approximateInvokeCount": 1
  },
  "requestPayload": {
    "Records": [{ "s3": { "bucket": {...}, "object": {...} } }]
  },
  "responsePayload": {
    "statusCode": 200,
    "body": "..."
  }
}
```

Both the **original event** (requestPayload) and the **Lambda response** (responsePayload) included!

### Testing Failure
1. Modify Lambda code: `raise Exception("boom!")`
2. Upload `index.html` to S3 → triggers Lambda
3. Lambda fails → **retries 2 more times** (async behavior)
4. After ~3 minutes (retries exhausted) → message appears in `s3-failure`

**Failure message body contains:**
```json
{
  "requestContext": {
    "condition": "RetriesExhausted",
    "approximateInvokeCount": 3
  },
  "requestPayload": {
    "Records": [{ "s3": { "bucket": {...}, "object": {...} } }]
  },
  "responsePayload": {
    "errorMessage": "boom!",
    "errorType": "Exception",
    "stackTrace": ["..."]
  }
}
```

Contains: original event, error message, error type, and **stack trace** — everything needed to debug.

### Key Observation: Failure Destination is NOT Immediate

Because S3 → Lambda is async, Lambda retries **3 times** before sending to the failure destination. That's why the message took ~3 minutes to appear (immediate + 1 min + 2 min).

---

## Exam Tips

- Destination messages include BOTH the **original event** and the **Lambda response/error**
- DLQ only sends the original event — Destinations send much more info
- Lambda console **auto-adds** SQS permissions when you configure destinations
- Failure destination waits for **all retries to exhaust** before sending (async = 3 attempts)
- Destination source types available: **Asynchronous invocation** or **Stream invocation** (Kinesis/DDB)
