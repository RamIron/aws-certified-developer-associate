Event Source Mapping Deep DiveEvent Source Mapping en Detalle

Streams vs Queues — different scaling, ordering, and error handling behaviorsStreams vs Colas — diferente escalado, orden y manejo de errores

Event Source Mapping is a Lambda internal component that polls a source on your behalf — you don't invoke Lambda directly. It reads batches of records from Kinesis, DynamoDB Streams, or SQS and invokes your function synchronously with those batches. The key distinction: with streams (Kinesis/DynamoDB) ordering is preserved per shard and a stuck record blocks the shard; with queues (SQS) records are independent and can be processed in parallel. Event Source Mapping es un componente interno de Lambda que hace polling a la fuente en tu nombre — no invocás Lambda directamente. Lee lotes de registros de Kinesis, DynamoDB Streams o SQS e invoca tu función sincrónicamente con esos lotes. La diferencia clave: con streams (Kinesis/DynamoDB) el orden se preserva por shard y un registro bloqueado traba el shard; con colas (SQS) los registros son independientes y se pueden procesar en paralelo.

La diferencia entre CF Functions y Lambda@Edge es en qué etapas puede interceptar tu código. CF Functions solo puede modificar el lado del viewer (①④). Lambda@Edge puede interceptar las 4, incluyendo el lado del origin (②③) — ese es su poder extra clave. Origin es tu backend real: S3, EC2, ALB o API GW.

Lambda ConcurrencyConcurrencia de Lambda

Account LimitLímite de Cuenta

  • 1,000 concurrent (default)concurrentes (default)
  • Shared across ALL functionsCompartido entre TODAS las funciones

Reserved ConcurrencyConcurrencia Reservada

  • Per-function cap — sets the maximum number of concurrent executions this function can have. The rest of the account's concurrency pool is unaffected. Tope por función — define el máximo de ejecuciones simultáneas que puede tener. El resto del pool de concurrencia de la cuenta no se ve afectado.
  • Prevents one function from stealing all capacity — without this, a spiky function could consume the account's entire 1000-concurrent limit, throttling every other function. Evita que una función robe toda la capacidad — sin esto, una función con picos podría consumir el límite total de 1000 de la cuenta y throttlear todas las demás.
  • Set to 0 = always throttled — every invocation is rejected immediately. Useful to disable a function without deleting it (e.g. emergency stop, cost control). Poner en 0 = siempre throttled — toda invocación es rechazada de inmediato. Útil para deshabilitar una función sin borrarla (ej: parada de emergencia, control de costos).

Provisioned ConcurrencyConcurrencia Aprovisionada

  • Pre-warm instances — Lambda initializes a set number of execution environments in advance, before any request arrives. You pay for them even when idle. Instancias pre-calentadas — Lambda inicializa una cantidad fija de entornos de ejecución de antemano, antes de que llegue cualquier request. Se paga por ellos aunque estén ociosos.
  • No cold starts!¡Sin cold starts!
    Since the environment is already initialized, the first request is as fast as any subsequent one. Critical for latency-sensitive apps (e.g. APIs, real-time processing). Como el entorno ya está inicializado, el primer request es tan rápido como cualquier otro. Crítico para apps sensibles a la latencia (ej: APIs, procesamiento en tiempo real).
  • Set on versions/aliases, NOT $LATEST — because $LATEST changes with every deploy, AWS can't keep a stable warm pool for it. You must pin to a specific version or alias. Configurar en versiones/aliases, NO $LATEST — porque $LATEST cambia con cada deploy, AWS no puede mantener un pool estable para él. Hay que apuntar a una versión o alias específico.
Why pre-warm? Normally, the first time Lambda runs (or after a period of inactivity), AWS has to spin up a new execution environment: download your code, start the runtime, run your initialization code. This is the cold start — it adds hundreds of milliseconds of latency. With Provisioned Concurrency, AWS keeps N environments already initialized and ready. Example: an API that handles checkout requests can't afford a 500ms delay on the first request after midnight — you'd set Provisioned Concurrency = 5 to guarantee 5 instantly-ready instances at all times. ¿Para qué pre-calentar? Normalmente, la primera vez que Lambda corre (o tras un período de inactividad), AWS tiene que arrancar un nuevo entorno: descargar el código, iniciar el runtime, ejecutar el código de inicialización. Eso es el cold start — agrega cientos de milisegundos de latencia. Con Provisioned Concurrency, AWS mantiene N entornos ya inicializados y listos. Ejemplo: una API que maneja pedidos de checkout no puede permitirse 500ms de delay en el primer request después de medianoche — configurarías Provisioned Concurrency = 5 para garantizar 5 instancias listas al instante en todo momento.

Tricky Quiz Questions Preguntas Tricky del Quiz

DLQ configured to send to SNS, but failed events never arrive — CloudWatch confirms failures exist. Why? DLQ configurada para enviar a SNS, pero los eventos fallidos nunca llegan — CloudWatch confirma que hay fallos. ¿Por qué?

✅ Lambda's execution role is missing permissions to publish to SNS ✅ El execution role de Lambda no tiene permisos para publicar en SNS

The trap is thinking SNS isn't supported as a DLQ — it is (alongside SQS). The real issue is that Lambda needs explicit IAM permissions in its execution role to publish to the DLQ destination. Without sns:Publish on the topic ARN, Lambda silently fails to deliver the failed event, even though CloudWatch still records the function failure. La trampa es creer que SNS no está soportado como DLQ — sí lo está (junto con SQS). El problema real es que Lambda necesita permisos IAM explícitos en su execution role para publicar en el destino de la DLQ. Sin sns:Publish en el ARN del topic, Lambda falla silenciosamente al entregar el evento fallido, aunque CloudWatch igual registre el fallo de la función.

X-Ray integration is enabled on Lambda but it doesn't work. What is a possible cause? X-Ray está habilitado en Lambda pero no funciona. ¿Cuál es una posible causa?

✅ Check IAM permissions in the Lambda execution role ✅ Verificar permisos IAM en el execution role de Lambda

The trap is thinking you need to bundle the X-Ray daemon in your deployment package — you don't. Lambda runs the daemon automatically when Active Tracing is enabled. What breaks silently is missing AWSXRayDaemonWriteAccess in the execution role: the daemon runs but can't send segments to X-Ray. La trampa es creer que hay que incluir el daemon de X-Ray en el paquete de deploy — no hace falta. Lambda lo corre automáticamente cuando habilitás Active Tracing. Lo que falla silenciosamente es que falte AWSXRayDaemonWriteAccess en el execution role: el daemon corre pero no puede enviar segmentos a X-Ray.

Lambda needs to send an 8 KB token to a 3rd party API. Where should you place this token? Lambda necesita enviar un token de 8 KB a una API de terceros. ¿Dónde debería almacenarlo?

✅ Place it in the deployment package (.zip file) ✅ Incluirlo en el deployment package (archivo .zip)

The trap is environment variables — they seem like the natural place for tokens/secrets, but Lambda env vars have a hard limit of 4 KB total. An 8 KB token exceeds that, so it can't go there. The answer is to bundle it in the deployment package itself. La trampa son las variables de entorno — parecen el lugar natural para tokens/secretos, pero las env vars de Lambda tienen un límite de 4 KB total. Un token de 8 KB lo supera, así que no cabe ahí. La respuesta es incluirlo directamente en el deployment package.

Lambda opens a new DB connection on every invocation, degrading RDS performance. How do developers fix this with long-lived connections? Lambda abre una nueva conexión a la DB en cada invocación, degradando el rendimiento de RDS. ¿Cómo lo solucionan los developers con conexiones de larga duración?

✅ Move the database connection object outside of the function handler ✅ Mover el objeto de conexión a la DB fuera del function handler

This is execution context reuse: anything initialized outside the handler persists in the execution environment as long as Lambda reuses the same container. The DB connection is opened once and reused across subsequent invocations — instead of opening and closing on every call. The trap is thinking Lambda containers are always destroyed after each call — they're not, AWS reuses them for performance. Esto es reutilización del contexto de ejecución: todo lo que se inicializa fuera del handler persiste en el entorno de ejecución mientras Lambda reutilice el mismo contenedor. La conexión a la DB se abre una vez y se reutiliza en invocaciones posteriores — en vez de abrirse y cerrarse en cada llamada. La trampa es creer que los contenedores de Lambda siempre se destruyen tras cada llamada — no es así, AWS los reutiliza por performance.

Lambda (Node.js) needs a PostgreSQL driver as a dependency. How do you bundle it? Lambda (Node.js) necesita un driver de PostgreSQL como dependencia. ¿Cómo lo empaquetás?

✅ Put the function and dependencies in one folder and zip them together ✅ Poner la función y las dependencias en una carpeta y zipearlas juntas

Lambda does not resolve dependencies for you — it won't read a package.json and run npm install. You must run npm install locally first, then zip your code together with the resulting node_modules folder and upload that. The trap is the package.json option — it sounds reasonable but Lambda has no build step. Lambda no resuelve dependencias por vos — no va a leer un package.json y correr npm install. Tenés que correr npm install localmente primero, luego zipear tu código junto con la carpeta node_modules resultante y subir ese zip. La trampa es la opción del package.json — suena razonable pero Lambda no tiene paso de build.

Which AWS service allows you to schedule a Lambda function to be invoked every hour? ¿Qué servicio de AWS permite invocar una función Lambda de forma programada cada hora?

✅ Amazon EventBridge

EventBridge (formerly CloudWatch Events) supports cron and rate-based schedules to trigger Lambda automatically. SQS triggers Lambda reactively (when messages arrive), not on a schedule. Kinesis and S3 are event-driven by data, not time. EventBridge (antes CloudWatch Events) soporta schedules con cron o rate para disparar Lambda automáticamente. SQS dispara Lambda de forma reactiva (cuando llegan mensajes), no por horario. Kinesis y S3 son event-driven por datos, no por tiempo.

Which allows you to deploy Lambda globally so CloudFront requests are filtered at AWS Edge Locations? ¿Qué permite desplegar Lambda globalmente para que los requests de CloudFront se filtren en los Edge Locations?

✅ Lambda@Edge

Lambda@Edge is the only Lambda deployment model that ties directly into CloudFront and runs at edge locations globally. You author in us-east-1 and CloudFront replicates it. Regular Lambda runs in a single region — it can't intercept CloudFront traffic at the edge. Lambda@Edge es el único modelo de deploy de Lambda que se integra directamente con CloudFront y corre en los edge locations globalmente. Se crea en us-east-1 y CloudFront lo replica. Lambda regular corre en una sola región — no puede interceptar tráfico de CloudFront en el edge.

To use Lambda with an ALB, the function must be registered with ........? Para usar Lambda con un ALB, la función debe registrarse en ........?

✅ A Target Group

ALB treats Lambda exactly like an EC2 instance — it must be registered in a Target Group, which the ALB listener rule points to. The trap is Event Source Mapping, which is an unrelated concept: it's the internal Lambda component that polls Kinesis, DynamoDB Streams, and SQS. It has nothing to do with ALB. ALB trata a Lambda igual que a una instancia EC2 — debe registrarse en un Target Group al que apunta la regla del listener del ALB. La trampa es Event Source Mapping, que es un concepto distinto: es el componente interno de Lambda que hace polling a Kinesis, DynamoDB Streams y SQS. No tiene nada que ver con ALB.

S3 Event Notification triggers Lambda. You see duplicate CloudWatch logs with the same request ID. Why? S3 Event Notification dispara Lambda. Ves logs duplicados en CloudWatch con el mismo request ID. ¿Por qué?

✅ The Lambda function failed and retries happenedLa función falló y hubo reintentos

S3 → Lambda is an asynchronous invocation. On failure, Lambda automatically retries up to 2 more times. Each retry reuses the same request ID as the original attempt — that's why the logs appear duplicated with the same ID. If S3 had invoked Lambda independently twice, the request IDs would be different. The same-ID clue tells you it's a retry, not a duplicate trigger. S3 → Lambda es una invocación asíncrona. Ante un fallo, Lambda reintenta automáticamente hasta 2 veces más. Cada reintento reutiliza el mismo request ID del intento original — por eso los logs aparecen duplicados con el mismo ID. Si S3 hubiera invocado Lambda dos veces de forma independiente, los request IDs serían distintos. El mismo ID es la clave: es un retry, no un trigger duplicado.

Which service does NOT require a Lambda Event Source Mapping? (Kinesis Data Streams / DynamoDB Streams / SQS / SNS) ¿Qué servicio NO requiere un Event Source Mapping de Lambda? (Kinesis / DynamoDB Streams / SQS / SNS)

✅ SNS

Event Source Mapping is a polling mechanism — Lambda pulls records from the source. It applies to Kinesis Data Streams, DynamoDB Streams, and SQS. SNS uses a push model: SNS invokes Lambda directly as a subscriber, no polling needed. The trap is assuming DynamoDB Streams doesn't need it (it does — Lambda polls the stream). Event Source Mapping es un mecanismo de polling — Lambda va a buscar registros a la fuente. Se usa con Kinesis Data Streams, DynamoDB Streams y SQS. SNS usa modelo push: SNS invoca Lambda directamente como suscriptor, sin polling. La trampa es asumir que DynamoDB Streams no lo necesita (sí lo necesita — Lambda hace polling del stream).

Python Lambda with heavy native dependencies — each deploy takes 15 min to compile them. What do you suggest? Lambda en Python con dependencias nativas pesadas — cada deploy tarda 15 min en compilarlas. ¿Qué sugerís?

✅ Create a Lambda Layer and include all the dependencies in itCrear un Lambda Layer con todas las dependencias

A Lambda Layer is a separate, versioned ZIP that gets mounted at /opt in the execution environment. You compile and publish the dependencies once as a layer; your function code stays small and deploys instantly. The layer is reused across invocations and function versions — you only re-publish it when the dependencies themselves change. Un Lambda Layer es un ZIP separado y versionado que se monta en /opt del entorno de ejecución. Compilás y publicás las dependencias una sola vez como layer; el código de la función queda liviano y se despliega al instante. El layer se reutiliza entre invocaciones y versiones de la función — solo se re-publica cuando cambian las dependencias.

Which Lambda feature CANNOT be used to create a custom runtime? (Layers / Destinations / Container Images) ¿Qué feature de Lambda NO puede usarse para crear un runtime personalizado? (Layers / Destinations / Container Images)

✅ Lambda Destinations

Layers and Container Images both support custom runtimes: a Layer can include a bootstrap executable for any language (Rust, COBOL, etc.) using the provided.al2 runtime; a Container Image lets you package any runtime inside a Docker image. Destinations is completely unrelated to runtimes — it routes the result of an async invocation (success or failure) to SQS, SNS, EventBridge, or another Lambda function. Layers y Container Images soportan runtimes personalizados: un Layer puede incluir un ejecutable bootstrap para cualquier lenguaje (Rust, COBOL, etc.) usando el runtime provided.al2; una Container Image permite empaquetar cualquier runtime en Docker. Destinations no tiene nada que ver con runtimes — enruta el resultado de una invocación asíncrona (éxito o fallo) hacia SQS, SNS, EventBridge, u otra función Lambda.
