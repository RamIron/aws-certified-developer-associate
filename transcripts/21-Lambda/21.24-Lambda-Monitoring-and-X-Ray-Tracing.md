# 21.24 - Lambda Monitoring & X-Ray Tracing

> Udemy Lecture #287 · Section 21: AWS Serverless: Lambda

## Key Concepts

### 1. CloudWatch Logs

- Lambda execution logs → **automatically** stored in CloudWatch Logs
- Requires: IAM execution role with CloudWatch Logs permissions (included in **BasicExecutionRole**)

### 2. CloudWatch Metrics

Available in CloudWatch Metrics UI or Lambda UI:

| Metric | What It Shows |
|--------|--------------|
| **Invocations** | Number of times function was called |
| **Duration** | How long each execution took |
| **Concurrent Executions** | How many instances running at same time |
| **Error Count** | Number of failed invocations |
| **Success Rate** | Percentage of successful invocations |
| **Throttles** | Invocations rejected due to concurrency limits |
| **Async Delivery Failures** | Failed async invocations |
| **Iterator Age** | How far behind Lambda is reading from Kinesis/DDB streams (lag) |

### 3. X-Ray Tracing

Enable tracing in Lambda:

```
┌────────────────────────────────────────────────┐
│  Step 1: Enable "Active Tracing" in Lambda     │
│          (Lambda runs X-Ray daemon for you)    │
│                                                │
│  Step 2: Use X-Ray SDK in your code            │
│                                                │
│  Step 3: IAM execution role must have:         │
│          AWSXRayDaemonWriteAccess              │
└────────────────────────────────────────────────┘
```

No need to install daemon manually — Lambda handles it when Active Tracing is enabled.

### 4. X-Ray Environment Variables

When you enable Active Tracing, Lambda **automatically** sets these 3 env vars in your function's runtime. You don't create them — the X-Ray SDK reads them internally.

| Variable | What It Does | When You'd Care |
|----------|-------------|-----------------|
| `_X_AMZN_TRACE_ID` | The **tracing header** — unique trace ID that follows your request across services. The SDK reads this to know which trace this invocation belongs to. | If you need to manually propagate the trace to a downstream service |
| `AWS_XRAY_CONTEXT_MISSING` | What happens when code tries to use X-Ray but there's **no active trace context** (e.g., Active Tracing not enabled). Default: `LOG_ERROR` (logs a warning, doesn't crash). | Rarely — just know default is `LOG_ERROR` |
| **`AWS_XRAY_DAEMON_ADDRESS`** | **IP:PORT** of the X-Ray daemon (e.g., `169.254.79.129:2000`). The SDK uses this to know **where to send trace data**. | **Most important for exam** — how the SDK finds the daemon |

```
Lambda function starts with Active Tracing ON
       ↓
AWS auto-sets:
  _X_AMZN_TRACE_ID = "Root=1-abc123;Parent=def456;Sampled=1"
  AWS_XRAY_CONTEXT_MISSING = "LOG_ERROR"
  AWS_XRAY_DAEMON_ADDRESS = "169.254.79.129:2000"
       ↓
X-Ray SDK reads these → sends traces to daemon at that address
       ↓
Daemon sends to X-Ray service (batch every 1s, UDP)
```

These are accessed like any env var: `os.getenv("AWS_XRAY_DAEMON_ADDRESS")` in Python.

## Exam Tips

- Lambda logs → **CloudWatch Logs** (automatic, needs BasicExecutionRole)
- Lambda metrics → **CloudWatch Metrics** (invocations, duration, errors, throttles)
- **Iterator Age** metric = how far behind in reading Kinesis/DDB streams
- X-Ray on Lambda: enable **Active Tracing** + use **X-Ray SDK** + **AWSXRayDaemonWriteAccess** role
- Lambda runs the X-Ray daemon for you — no manual install
- Most important env var: **`AWS_XRAY_DAEMON_ADDRESS`** (IP:port of daemon)
- Connects to Section 20: same `AWSXRayWriteOnlyAccess` / `AWSXRayDaemonWriteAccess` concepts
