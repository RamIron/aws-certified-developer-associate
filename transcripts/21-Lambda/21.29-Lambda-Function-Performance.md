# 21.29 - Lambda Function Performance

> **Lecture 292** | Section 21: AWS Serverless: Lambda
> Tuning RAM, timeout, execution context, and /tmp to optimize Lambda performance

---

## RAM & vCPU

- Default: **128 MB** RAM
- Max: **10 GB** RAM (1 MB increments)
- **You cannot set vCPUs directly** — you increase RAM to implicitly get more vCPU
- At **1,792 MB** of RAM → function gets the equivalent of **1 full vCPU**
- Above 1,792 MB → more than 1 vCPU → need **multi-threading** to benefit

```
  RAM              vCPU
  ─────────────────────────────
  128 MB           fractional
  1,792 MB    →    1 full vCPU
  3,584 MB    →    2 vCPUs
  10,240 MB   →    ~6 vCPUs
  ─────────────────────────────
  More RAM = More CPU = More Network
```

> **Exam tip:** If Lambda is CPU-bound (heavy computation) and you want to improve performance → **increase RAM** (not a direct vCPU setting)

---

## Timeout

- **Default:** 3 seconds
- **Maximum:** 900 seconds (15 minutes)
- Anything over 15 minutes → NOT a Lambda use case → use **Fargate, ECS, or EC2**

## Execution Context (Key Performance Concept!)

The execution context is a **temporary runtime environment** that persists between invocations. AWS keeps it alive anticipating the next call.

### Bad Code vs Good Code

```python
# ❌ BAD — DB connection INSIDE handler (runs EVERY invocation)
def get_user_handler(event, context):
    DB_URL = os.getenv("DB_URL")
    db_client = database.connect(DB_URL)    # ← runs every time!
    user = db_client.get(user_id=event["user_id"])
    return user
```

```python
# ✅ GOOD — DB connection OUTSIDE handler (runs ONCE, reused)
DB_URL = os.getenv("DB_URL")
db_client = database.connect(DB_URL)        # ← runs once, reused!

def get_user_handler(event, context):
    user = db_client.get(user_id=event["user_id"])
    return user
```

```
  ┌─────────────────────────────────────────────┐
  │  Execution Context (persists between calls)  │
  │                                               │
  │  ┌─────────────────────────────────────┐     │
  │  │  DB connections, HTTP clients,       │     │
  │  │  SDK clients initialized HERE        │     │
  │  │  (OUTSIDE the handler)               │     │
  │  └─────────────────────────────────────┘     │
  │                                               │
  │  ┌─────────────────────────────────────┐     │
  │  │  Handler function                    │     │
  │  │  (only business logic here)          │     │
  │  └─────────────────────────────────────┘     │
  │                                               │
  │  ┌─────────────────────────────────────┐     │
  │  │  /tmp directory (10 GB)              │     │
  │  │  (files persist across invocations)  │     │
  │  └─────────────────────────────────────┘     │
  └─────────────────────────────────────────────┘
```

> **Rule:** Anything heavy to initialize (DB connections, HTTP clients, SDK clients) → put **OUTSIDE** the handler → reused across invocations

---

## /tmp Directory

- **Size:** Up to **10 GB** of disk space
- **Purpose:** Write temporary files (download large files, disk operations)
- **Persists** across invocations within the same execution context
- If you need **permanent** storage → use **S3** instead
- To **encrypt** content in /tmp → use **KMS data keys** (generate key, encrypt yourself — no built-in /tmp encryption setting)

## Exam Tips

- **CPU-bound Lambda?** → increase **RAM** (vCPU scales with RAM)
- **1,792 MB** = 1 full vCPU. Above that → multi-threading needed
- **Timeout max** = 15 minutes. More than that → NOT Lambda
- Exam shows pseudocode → look for **where connections are initialized**:
  - Inside handler = bad (runs every time)
  - Outside handler = good (reused via execution context)
- **/tmp** = 10 GB, temporary, persists within execution context
- **/tmp encryption** = use **KMS data keys** (no built-in setting)
- Need permanent storage? → **S3**, not /tmp
