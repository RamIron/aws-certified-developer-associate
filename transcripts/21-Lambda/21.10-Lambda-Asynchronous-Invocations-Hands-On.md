# 21.10 - Lambda Asynchronous Invocations Hands On

> Udemy Lecture #273 · Section 21: AWS Serverless: Lambda

## Hands-On Summary

### Async Invocation via CLI

```bash
aws lambda invoke \
  --function-name demo-lambda \
  --invocation-type Event \
  --payload '{"key1":"value1"}' \
  response.json
```

- Returns **status code 202** (accepted) — NOT 200
- 202 = "I received it, I'll process it later"
- Same 202 whether the function **succeeds or fails** — you don't know the result
- To see what happened → check **CloudWatch Logs**

### Key Observation: 202 vs 200

```
Synchronous  → 200 (success) or error code → you KNOW the result
Asynchronous → 202 always → you DON'T know the result
```

### Retries in CloudWatch Logs

When the function fails with retries = 2, CloudWatch shows:

```
Request ID: 2ab... → FAIL (original)
Request ID: 2ab... → FAIL (retry 1, after ~1 min)
Request ID: 2ab... → FAIL (retry 2, after ~2 min)
→ same request ID for all 3 attempts!
```

### Setting Up DLQ

1. **Create SQS queue** → `lambda-DLQ` (standard queue)
2. **Lambda → Configuration → Asynchronous invocation → Edit**
   - Retry attempts: 0, 1, or 2 (default 2)
   - Dead-letter queue: select SQS queue
3. **Permission error!** Lambda needs `sqs:SendMessage` permission
4. **Fix**: Lambda execution role → attach `AmazonSQSFullAccess` policy
5. Save → now Lambda can write to SQS on failure

### DLQ Message in SQS

After all retries fail, message appears in SQS with:
- **Body**: the original event payload
- **Message attributes**: error cause, request ID (matches the Lambda invocation ID from CloudWatch Logs)

---

## Exam Tips

- Async invocation → **status 202** (accepted), not 200
- 202 regardless of success or failure — check CloudWatch Logs for actual result
- Same **request ID** across all retry attempts
- DLQ requires Lambda execution role to have **SQS SendMessage** permission
- Retry attempts configurable: **0, 1, or 2** (default 2, so 3 total attempts including original)
