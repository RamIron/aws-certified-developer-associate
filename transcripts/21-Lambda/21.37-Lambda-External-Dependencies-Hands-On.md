# 21.37 - Lambda External Dependencies - Hands On

> **Lecture 300** | Section 21: AWS Serverless: Lambda
> Packaging X-Ray SDK with Lambda, uploading via CLI, and tracing with X-Ray

---

## What Was Demonstrated

### 1. Packaging Dependencies in CloudShell
- Created a `lambda/` folder in CloudShell (has npm pre-installed)
- Created `index.js` that requires `aws-xray-sdk-core` and calls `S3.listBuckets()`
- Ran `npm install aws-xray-sdk` → creates `node_modules/` with all dependencies
- Set file permissions with `chmod`
- Zipped everything: `zip -r function.zip .`

### 2. Uploading via CLI
- Created an IAM role (`demo-lambda-with-dependencies`) with `AWSLambdaBasicExecutionRole`
- Used `aws lambda create-function` CLI command with the zip file and role ARN
- Could also upload via console: Code Source → Upload from → .zip file or S3 location

### 3. Fixing Permissions
- First test → **Access Denied** (no S3 permissions)
- Enabled **X-Ray Active Tracing** → added `AWSXRayDaemonWriteAccess` automatically
- Attached **AmazonS3ReadOnlyAccess** to the role
- Second/third test → **Success** (ListBuckets returned all buckets)

### 4. X-Ray Traces
- Service map showed: Client → Lambda → S3
- Failed trace: 403 error on ListBuckets (Access Denied) — clearly visible in X-Ray
- Successful trace: showed invocation timing, S3 call duration, response time
- X-Ray is very helpful for debugging permission issues and performance

---

## Key Takeaways

- **CloudShell** is convenient for packaging Lambda (npm/pip already installed)
- `npm install` + `zip` + `aws lambda create-function` = deploy with dependencies from CLI
- Upload methods: direct zip (< 50 MB), S3 location, or console upload
- X-Ray traces show **exactly where and why** failures happen (403, Access Denied, etc.)
