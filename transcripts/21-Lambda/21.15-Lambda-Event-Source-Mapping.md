# 21.15 - Lambda Event Source Mapping

> Udemy Lecture #278 · Section 21: AWS Serverless: Lambda

## Key Concepts

### 1. The Third Invocation Model

Three ways Lambda gets invoked:

- **Synchronous**: caller waits (ALB, API Gateway, CLI)
- **Asynchronous**: fire & forget, Lambda retries (S3, SNS, EventBridge)
- **Event Source Mapping**: Lambda **polls** the source (Kinesis, DynamoDB Streams, SQS)

```
┌────────────────────┐     poll      ┌─────────────────┐
│  Kinesis / DDB /   │ ←───────────  │  Event Source   │
│  SQS               │ ──batch──→    │  Mapping        │
└────────────────────┘               └────────┬────────┘
                                              │ sync invoke
                                              ↓
                                     ┌─────────────────┐
                                     │     Lambda      │
                                     │    Function     │
                                     └─────────────────┘
```

Event Source Mapping is an internal Lambda component that polls the source, gets a **batch** of records, then invokes Lambda **synchronously**.

### 2. Streams (Kinesis Data Streams & DynamoDB Streams)

- A **shard** = one lane in the stream highway. Records are distributed across shards by partition key.
- Creates an **iterator per shard** — items processed **in order** within each shard
- **Start position** (configured once when setting up the mapping):
  - `LATEST` — only new records from now on
  - `TRIM_HORIZON` — from the very beginning of the shard
  - `AT_TIMESTAMP` — from a specific point in time
- Processed items are **NOT removed** from the shard — they stay until they expire (24h–365 days). Other consumers (another Lambda, analytics app) can read the same data independently.
- **Low traffic**: use batch window to accumulate records before invoking
- **High traffic**: enable parallelization — up to **10 batch processors per shard**
  - In-order processing maintained at **partition key level**

**Parallelization diagram (from AWS blog):**

```
                         ┌──────────┐  Invoker   ┌──────┐
                    ┌──→ │ Batcher1 │ ────────→  │  λ   │
┌───────────┐       │    │  [1] [1] │            └──────┘
│  A shard  │  Record    ├──────────┤  Invoker   ┌──────┐
│ [3][1][2] │→ Processor │ Batcher2 │ ────────→  │  λ   │
│   [1]     │  (hashing) │   [2]    │            └──────┘
└───────────┘       │    ├──────────┤  Invoker   ┌──────┐
                    └──→ │ Batcher3 │ ────────→  │  λ   │
                         │   [3]    │            └──────┘
                         └──────────┘
```

Records with the same partition key (color) go to the same batcher → in-order per key.

**Scaling:**

- Default: **1 Lambda invocation per shard**
- With parallelization: up to **10 batches per shard simultaneously**

**Parallelization Factor** = how many Lambda instances process each shard simultaneously.
Total concurrent invocations = **shards × parallelization factor**

```
Example: 4 shards, parallelization factor = 5

  Shard 1 → 5 Lambda instances  ┐
  Shard 2 → 5 Lambda instances  │
  Shard 3 → 5 Lambda instances  ├→ Total: 4 × 5 = 20 concurrent Lambdas
  Shard 4 → 5 Lambda instances  ┘

Default (no parallelization, factor = 1):
  Shard 1 → 1 Lambda  ┐
  Shard 2 → 1 Lambda  ├→ Total: 4 × 1 = 4 concurrent Lambdas
  Shard 3 → 1 Lambda  │
  Shard 4 → 1 Lambda  ┘
```

Max parallelization factor = **10** → so a stream with 4 shards can have at most 4 × 10 = **40** concurrent Lambdas.

### 3. Stream Error Handling

If function returns an error on a batch:

- **Entire batch is reprocessed** until success or items expire
- Processing for that shard is **paused** (blocks the shard!)

Options to handle:

- **Discard old events** (send to a Destination)
- **Limit retry attempts**
- **Split batch on error** (useful for Lambda timeout — process half the batch)

### 4. Queues (SQS & SQS FIFO)

- Event Source Mapping polls SQS using **Long Polling**
- Batch size: **1 to 10 messages**
- Recommended: queue visibility timeout = **6x Lambda function timeout**
- DLQ? Set it on **SQS**, NOT on Lambda (Lambda DLQ only works for async invocations)
- Successfully processed items are **deleted from the queue** by Lambda
- Occasionally may receive the **same item twice** → function must be **idempotent**

### 5. SQS Standard vs FIFO Scaling

|              | SQS Standard                                                                               | SQS FIFO                                 |
| ------------ | ------------------------------------------------------------------------------------------ | ---------------------------------------- |
| **Order**    | No ordering guarantee                                                                      | In-order per Message Group ID            |
| **Scaling**  | Adds 60 instances/min (60 per min), up to **1,000 batches/sec**                            | Scales to # of **active message groups** |
| **On error** | Batch items returned individually to queue, next poll may grab a different mix of messages | Processed in order per group             |

### 6. Summary: Three Invocation Models

|                    | Synchronous           | Asynchronous         | Event Source Mapping            |
| ------------------ | --------------------- | -------------------- | ------------------------------- |
| **Who triggers**   | User/service directly | Service fires event  | Lambda polls source             |
| **Waits?**         | Yes                   | No                   | Lambda polls, then invokes sync |
| **Retries**        | Client handles        | Lambda retries (3x)  | Depends on source (see above)   |
| **Error handling** | Client-side           | DLQ on Lambda        | DLQ on SQS / Destination        |
| **Services**       | ALB, API GW, CLI      | S3, SNS, EventBridge | Kinesis, DynamoDB Streams, SQS  |

## Exam Tips

- Event Source Mapping = Lambda **polls** the source → invokes function **synchronously** with a batch
- Streams: error **blocks the shard** until resolved — use discard/retry limits/split batch
- SQS: DLQ goes on **SQS queue**, NOT on Lambda (Lambda DLQ = async only)
- SQS visibility timeout = **6x Lambda timeout** (AWS recommendation)
- SQS Standard: up to **1,000 batches/sec**
- SQS FIFO: scales to **# of active message groups**
- Streams parallelization: up to **10 batches per shard**
- Items NOT removed from streams (Kinesis/DDB) but ARE deleted from SQS after processing
- Event Source Mapping can receive same item twice → **idempotent** processing required
