# 21.27 - Lambda in VPC

> **Lecture 290** | Section 21: AWS Serverless: Lambda
> How Lambda accesses private resources and the internet when deployed inside a VPC

---

## Default Lambda Networking

By default, Lambda functions run **outside your VPC** (in an AWS-managed VPC). This means:

- ✅ Can access **public internet** (external APIs, websites)
- ✅ Can access **AWS public services** (DynamoDB, S3, etc.)
- ❌ **Cannot access private resources** in your VPC (RDS, ElastiCache, internal ELB)

```
  ┌─────────────────────────────────────────────┐
  │  AWS-managed network (default)              │
  │                                              │
  │  ┌──────────┐    ✅ Public Internet          │
  │  │  Lambda   │───► ✅ DynamoDB, S3           │
  │  └──────────┘    ❌ Your VPC (RDS, etc.)     │
  └─────────────────────────────────────────────┘
```

---

## Deploying Lambda in a VPC

To access private VPC resources, you configure Lambda with:

1. **VPC ID**
2. **Subnets** (private subnets)
3. **Security Group** for the Lambda function

Behind the scenes, Lambda creates an **ENI (Elastic Network Interface)** in the selected subnets. To create the ENI, Lambda needs the **AWSLambdaVPCAccessExecutionRole**.

```
  ┌─────────────── Your VPC ───────────────────┐
  │                                             │
  │  ┌─── Private Subnet ───────────────────┐  │
  │  │                                       │  │
  │  │  ┌──────────┐   ENI   ┌───────────┐  │  │
  │  │  │  Lambda   │────────►│    RDS     │  │  │
  │  │  │          │         │           │  │  │
  │  │  └──────────┘         └───────────┘  │  │
  │  │   Lambda SG ──────────► RDS SG       │  │
  │  │         (SG must allow access)       │  │
  │  └──────────────────────────────────────┘  │
  └─────────────────────────────────────────────┘
```

> **Important:** RDS security group must allow inbound traffic from the Lambda security group (same concept as EC2 → RDS)

---

## Lambda in VPC — Internet Access

### The Trap (Exam Favorite!)

- Lambda in a VPC **does NOT have internet access** by default
- Deploying Lambda in a **public subnet does NOT give it internet access or a public IP**
- This is **different from EC2** — EC2 in public subnet gets internet, Lambda does NOT

### The Solution: NAT Gateway

Deploy Lambda in a **private subnet** and route traffic through a **NAT Gateway/Instance** in a public subnet:

```
  ┌─────────────── Your VPC ────────────────────────────┐
  │                                                      │
  │  ┌── Private Subnet ──┐   ┌── Public Subnet ──┐     │
  │  │                     │   │                    │     │
  │  │  ┌──────────┐      │   │  ┌─────────────┐  │     │
  │  │  │  Lambda   │──────┼──►│  │ NAT Gateway  │  │     │
  │  │  └──────────┘      │   │  └──────┬──────┘  │     │
  │  │       │             │   │         │         │     │
  │  │       ▼             │   │         ▼         │     │
  │  │  ┌──────────┐      │   │  ┌─────────────┐  │     │
  │  │  │   RDS     │      │   │  │ Internet GW  │──┼──► Internet
  │  │  └──────────┘      │   │  └─────────────┘  │     │
  │  └─────────────────────┘   └────────────────────┘     │
  └──────────────────────────────────────────────────────┘
```

## Accessing AWS Services Privately: VPC Endpoints

For AWS services like **DynamoDB**, you have two options from a VPC:

1. **Public route:** Lambda → NAT Gateway → Internet Gateway → DynamoDB (works, but goes through internet)
2. **VPC Endpoint:** Lambda → VPC Endpoint Gateway → DynamoDB (private, no NAT/IGW needed)

```
  ┌─── Private Subnet ────────────────────────┐
  │                                            │
  │  ┌──────────┐     ┌──────────────────┐    │
  │  │  Lambda   │────►│  VPC Endpoint    │────┼──► DynamoDB
  │  └──────────┘     │  (Gateway type)   │    │   (private)
  │                    └──────────────────┘    │
  └────────────────────────────────────────────┘
```

> VPC Endpoints let you access AWS services **privately** without NAT or Internet Gateway

---

## CloudWatch Logs Exception

Lambda in a VPC can always write to **CloudWatch Logs** even without a NAT Gateway or VPC Endpoint. It works regardless.

---

## Exam Tips

- **Default Lambda** = outside your VPC → can't access private resources (RDS, ElastiCache)
- To access private resources → deploy Lambda **in VPC** with VPC ID + subnets + security group
- Lambda creates an **ENI** in your subnet → needs **AWSLambdaVPCAccessExecutionRole**
- **Lambda in public subnet ≠ internet access** (EXAM TRAP! Different from EC2!)
- For internet access → private subnet + **NAT Gateway** + Internet Gateway
- For private AWS service access → use **VPC Endpoints**
- **CloudWatch Logs always work** from Lambda in VPC (no NAT/endpoint needed)
