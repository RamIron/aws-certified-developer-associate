AWS Step Functions — Overview AWS Step Functions — Visión General

Step Functions lets you model any multi-step process as a state machine — a graph of states connected by transitions and conditions, defined in JSON and visualized automatically in the console. It is an orchestrator: it doesn't do compute itself, it tells other services (Lambda, ECS, DynamoDB…) when to run, waits for them, handles failures, and tracks every execution step-by-step. Step Functions permite modelar cualquier proceso multi-paso como una máquina de estados — un grafo de estados conectados por transiciones y condiciones, definido en JSON y visualizado automáticamente. Es un orquestador: no hace cómputo por sí mismo, le dice a otros servicios cuándo correr, espera por ellos, maneja fallas y registra cada ejecución paso a paso.

Step Functions — Error Handling Step Functions — Manejo de Errores

Error handling in Step Functions is defined in the state machine (ASL/JSON), not inside the application code (e.g., Lambda). This keeps Lambda functions small and fast, lets you change retry logic without redeploying, and gives you full execution history of every retry and catch directly in the console. There are two mechanisms: Retry (retry the failing task) and Catch (transition to a fallback state). El manejo de errores se define en la máquina de estados (ASL/JSON), no dentro del código de la aplicación. Esto mantiene Lambda pequeña y rápida, te permite cambiar la lógica de retry sin redesplegar, y te da historial completo de cada retry y catch en la consola. Hay dos mecanismos: Retry (reintentar la tarea) y Catch (ir a un estado de fallback).

Predefined Error Codes Códigos de Error Predefinidos

These are the built-in error codes you can reference in Retry and Catch blocks. Estos son los códigos de error integrados que podés usar en bloques Retry y Catch.

Complete ASL Example — Retry + Catch + ResultPath Ejemplo ASL Completo — Retry + Catch + ResultPath

A full Task state showing all error handling blocks together. The Retry array is evaluated first (top to bottom). If all retries are exhausted, the Catch array kicks in (also top to bottom). ResultPath on each catch entry controls what the fallback state receives. Un Task state completo mostrando todos los bloques de manejo de errores juntos. El array Retry se evalúa primero (de arriba hacia abajo). Si se agotan todos los retries, activa el array Catch (también de arriba hacia abajo). ResultPath en cada entrada de Catch controla qué recibe el estado de fallback. 

// A Task state with full error handling
"ProcessOrder": {
  "Type": "Task",
  "Resource": "arn:aws:lambda:us-east-1:123456789:function:ProcessOrder",

  // ── RETRY array (evaluated top → bottom) ─────────────────
  "Retry": [
    {
      "ErrorEquals": ["CustomError"],   // specific custom error first
      "IntervalSeconds": 1,              // wait 1s before first retry
      "BackoffRate": 2,                 // double the wait each time: 1s → 2s → 4s
      "MaxAttempts": 2                  // retry up to 2 times
    },
    {
      "ErrorEquals": ["States.TaskFailed"], // generic task failure
      "IntervalSeconds": 30,
      "BackoffRate": 2,
      "MaxAttempts": 2
    },
    {
      "ErrorEquals": ["States.ALL"],      // wildcard — always last!
      "IntervalSeconds": 5,
      "BackoffRate": 2,
      "MaxAttempts": 5
    }
  ],

  // ── CATCH array (kicks in when retries are exhausted) ─────
  "Catch": [
    {
      "ErrorEquals": ["CustomError"],
      "Next": "CustomErrorFallback",
      "ResultPath": "$.error"   // original input preserved + error at $.error
    },
    {
      "ErrorEquals": ["States.Timeout"],
      "Next": "TimeoutFallback",
      "ResultPath": null        // error discarded, only original input forwarded
    },
    {
      "ErrorEquals": ["States.ALL"],
      "Next": "CatchAllFallback"
                                  // no ResultPath → error replaces the entire input
    }
  ],

  "Next": "SuccessState"           // where to go if task succeeds
}

💡 Reading order: Retry[0] → Retry[1] → Retry[2] (each exhausts MaxAttempts) → then Catch[0] → Catch[1] → Catch[2] until one matches. 💡 Orden de lectura: Retry[0] → Retry[1] → Retry[2] (cada uno agota MaxAttempts) → luego Catch[0] → Catch[1] → Catch[2] hasta que uno coincida.

Step Functions — Wait For Task Token Step Functions — Wait For Task Token

waitForTaskToken lets a Step Functions task pause indefinitely until an external system signals back. Without it, Step Functions would fire a message and immediately move on — there'd be no way to wait for async work done outside AWS. Use it whenever your workflow depends on something external: human approval, a third-party API, a legacy system, or any async integration. waitForTaskToken permite que una tarea de Step Functions se pause indefinidamente hasta que un sistema externo señale de vuelta. Sin él, Step Functions dispararía el mensaje y seguiría de inmediato. Usalo cuando tu workflow depende de algo externo: aprobación humana, una API de terceros, un sistema legado, o cualquier integración async.

Use Cases Casos de Uso

Any scenario where work is done outside Step Functions before the workflow can continue. Cualquier escenario donde el trabajo se hace fuera de Step Functions antes de que el workflow pueda continuar.

Use caseCaso de uso

Legacy / on-premises system integrationIntegración con sistemas legados / on-premises
Another AWS service doing async workOtro servicio AWS haciendo trabajo async

Configuration Configuración

Two things are required in the task definition: appending the suffix to the Resource, and passing the token in the message body. Se requieren dos cosas en la definición de la tarea: agregar el sufijo al Resource, y pasar el token en el cuerpo del mensaje. 

"CheckClientCredits": {
  "Type": "Task",

  // Step 1 — append .waitForTaskToken to the resource
  "Resource": "arn:aws:states:::sqs:sendMessage.waitForTaskToken",

  "Parameters": {
    "QueueUrl": "https://sqs.us-east-1.amazonaws.com/123/MyQueue",
    "MessageBody": {
      "Input.$": "$",                  // pass the task input

      // Step 2 — include the token so the external system can call back
      "TaskToken.$": "$$.Task.Token"   // $$ = context object (not input)
    }
  },
  "Next": "SuccessState"
}

Full Flow Flujo Completo

The state machine pauses after sending the message. The external system receives the message, does its work, then calls back with the token. Step Functions matches the token and resumes. La máquina de estados se pausa tras enviar el mensaje. El sistema externo recibe el mensaje, hace su trabajo, y luego llama de vuelta con el token. Step Functions lo identifica y continúa.

Step Functions — Activity Tasks Step Functions — Activity Tasks

Activity Tasks let an external worker (EC2, Lambda, mobile, on-prem) poll Step Functions for work rather than being invoked by it. The worker regularly asks "anything for me?" using GetActivityTask, receives the input and a task token, does the work, and reports back — all while the state machine waits paused. Los Activity Tasks permiten que un worker externo (EC2, Lambda, móvil, on-prem) haga polling a Step Functions en busca de trabajo en lugar de ser invocado por él. El worker pregunta periódicamente con GetActivityTask, recibe el input y un task token, hace el trabajo y reporta — mientras la máquina de estados espera pausada.

Step Functions offers two workflow types optimized for opposite ends of the spectrum: Standard for long-running, reliable, non-idempotent workflows, and Express for short, extremely high-volume workloads. Express is further split into Asynchronous (at-least-once, fire-and-forget) and Synchronous (at-most-once, waits for result). Step Functions ofrece dos tipos de workflow optimizados para extremos opuestos: Standard para workflows largos, confiables y no-idempotentes, y Express para cargas de trabajo cortas y de altísimo volumen. Express se divide en Asynchronous (at-least-once, fire-and-forget) y Synchronous (at-most-once, espera el resultado).

AppSync is a managed AWS service for building GraphQL APIs. Instead of REST (where you get a fixed response from each endpoint), GraphQL lets the client specify exactly which fields it needs — AppSync fetches only that data from your sources and returns it. It has two exam angles: managed GraphQL API, and real-time / offline mobile sync. AppSync es un servicio managed de AWS para construir APIs GraphQL. A diferencia de REST (donde cada endpoint devuelve una respuesta fija), GraphQL permite que el cliente especifique exactamente qué campos necesita — AppSync busca solo esos datos en tus fuentes y los devuelve. Tiene dos ángulos en el examen: API GraphQL managed, y sincronización en tiempo real / offline para mobile.

Which AWS service does NOT support the WebSocket protocol? ¿Qué servicio de AWS NO soporta el protocolo WebSocket?

✅ DynamoDB

ALB, API Gateway, and AppSync all support WebSocket natively. DynamoDB is a database — it can trigger events via Streams → Lambda, but it has no WebSocket protocol support of its own. ALB, API Gateway y AppSync soportan WebSocket nativamente. DynamoDB es una base de datos — puede disparar eventos via Streams → Lambda, pero no tiene soporte WebSocket propio.
