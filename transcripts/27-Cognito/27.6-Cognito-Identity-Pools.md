# 27.6 — Cognito Identity Pools (Federated Identities)

## Summary
Cognito Identity Pools (also called Federated Identities) give **temporary AWS credentials** to external users (web/mobile) so they can directly access AWS services like S3 and DynamoDB — without creating IAM users for them.

---

## Key Concepts

### 1. What Problem It Solves
- External users (customers) need access to AWS resources (S3, DynamoDB, etc.)
- You can't create IAM users for them — too many, doesn't scale, untrusted
- Identity Pools bridge the gap: users trade an identity **token** for **temporary AWS credentials**

### 2. Supported Identity Providers
Users can log in through:
- **Public social providers**: Amazon, Facebook, Google, Apple
- **Amazon Cognito User Pools** (CUP) — most common combo
- **OpenID Connect (OIDC)** providers
- **SAML** providers
- **Developer Authenticated Identities** (custom login server)
- **Guest / Unauthenticated** users (with a restricted IAM policy)

### 3. Flow: Token → AWS Credentials
1. User logs in with any supported identity provider → gets a **token** (e.g. JWT from CUP)
2. App calls Cognito Identity Pool with that token
3. Identity Pool **verifies** the token with the provider
4. Identity Pool calls **STS** (`AssumeRoleForWebIdentity`) → gets temporary credentials
5. Credentials returned to the app → app calls AWS directly (S3, DynamoDB, etc.)

### 4. CUP + Identity Pools Together
- CUP stores and manages the users (central user DB, social logins, SAML, OIDC all flow in)
- CUP issues JWT → app sends JWT to Identity Pool → get AWS credentials
- This is the "full Cognito stack" pattern

### 5. IAM Role Mapping & Fine-Grained Access
- **Default IAM roles**: one for authenticated users, one for guest users
- **Rules**: map specific users (by user ID) to specific roles
- **Policy variables**: use `${cognito-identity.amazonaws.com:sub}` in IAM policies to restrict users to their own data:
  - S3: allow only prefix matching the user's ID → per-user folder
  - DynamoDB: allow only rows where leading key = user ID → row-level security

### 6. STS Call: AssumeRoleForWebIdentity
- Cognito Identity Pool calls STS with this API call
- The IAM roles must have a **trust policy** that allows `cognito-identity.amazonaws.com`

---

## Exam Tips
- CUP = authentication, returns **JWT** (not AWS credentials)
- Identity Pool = **AWS credentials** (via STS), for direct AWS resource access
- Guest users are supported — unauthenticated access with limited IAM policy
- Policy variables = fine-grained access (S3 prefix, DynamoDB leading key)
- STS API call: `AssumeRoleForWebIdentity`
- IAM roles need a trust policy pointing to Cognito Identity Pools
